## Шаг 1. Разбиваем программу на файлы

Задача-игрушка: посчитать сумму и среднее оценок. Логика подсчёта —
отдельно, вывод — отдельно. Создай пустой каталог и в нём два файла.

`stats.c` — только вычисления, никакого `printf`:

```c
int sum(const int *a, int n)
{
    int s = 0;
    for (int i = 0; i < n; i++)
        s += a[i];
    return s;
}

double average(const int *a, int n)
{
    if (n == 0)
        return 0.0;
    int s = sum(a, n);
    return s / n;
}
```

`main.c` — только ввод-вывод:

```c
#include <stdio.h>

int main(void)
{
    int marks[] = {5, 4, 5, 3, 4};
    int n = (int) (sizeof marks / sizeof marks[0]);

    printf("Сумма:   %d\n", sum(marks, n));
    printf("Среднее: %.2f\n", average(marks, n));
    return 0;
}
```

`sizeof marks / sizeof marks[0]` — размер всего массива в байтах,
делённый на размер одного элемента, то есть число элементов. Работает
только там, где `marks` — настоящий массив, а не указатель (каверза 2
приложения Б). Собираем как привыкли — по одному файлу:

```text
$ cc -std=c11 -Wall -Wextra main.c -o prog
main.c:8:34: error: call to undeclared function 'sum'; ISO C99 and
later do not support implicit function declarations
[-Wimplicit-function-declaration]
    8 |     printf("Сумма:   %d\n", sum(marks, n));
      |                             ^
main.c:9:38: error: call to undeclared function 'average'; ISO C99 and
later do not support implicit function declarations
[-Wimplicit-function-declaration]
    9 |     printf("Среднее: %.2f\n", average(marks, n));
      |                               ^
main.c:9:38: warning: format specifies type 'double' but the argument
has type 'int' [-Wformat]
    9 |     printf("Среднее: %.2f\n", average(marks, n));
      |                      ~~~~     ^~~~~~~~~~~~~~~~~
      |                      %.2d
1 warning and 2 errors generated.
```

(Строки с `error:` и `warning:` в терминале длинные и в одну строку —
здесь я их перенёс, чтобы влезли в страницу, как договаривались в
главе 1.)

Компилятор смотрит на **один файл за раз** и про `stats.c` ничего не
знает. Он видит вызов `sum(...)` и не знает ни сколько аргументов, ни
какой тип возвращается — отсюда и третья жалоба, про `%.2f`: раз тип
неизвестен, компилятор решил, что функция вернёт `int`.

Лечится **объявлением** (прототипом) — это заголовок функции без тела,
с точкой с запятой на конце: он ничего не создаёт, он обещает, что
такая функция где-то есть. Добавь в начало `main.c`:

```c
int sum(const int *a, int n);
double average(const int *a, int n);
```

```text
$ cc -std=c11 -Wall -Wextra main.c -o prog
Undefined symbols for architecture x86_64:
  "_average", referenced from:
      _main in main-408d4b.o
  "_sum", referenced from:
      _main in main-408d4b.o
ld: symbol(s) not found for architecture x86_64
clang: error: linker command failed with exit code 1 (use -v to see invocation)
```

Ошибка сменилась — и это прогресс. Теперь ругается не компилятор, а
**компоновщик** (linker) — программа, которая склеивает откомпилированные
куски в один исполняемый файл. Он ищет тела функций `sum` и `average` и
не находит: мы ему `stats.c` не дали. Подчёркивание перед именем
(`_sum`) добавляет сам компилятор, а `main-408d4b.o` — временный файл,
его случайный номер у тебя будет свой. Даём оба файла:

```text
$ cc -std=c11 -Wall -Wextra main.c stats.c -o prog
$ ./prog
Сумма:   21
Среднее: 4.00
```

Собралось и запустилось. (Среднее неправильное — 4.00 вместо 4.20. Это
не опечатка, мы вернёмся к этому на шаге 3.)

### Заголовочный файл

Прототипы в `main.c` работают, но это ловушка: поменяешь `sum` в
`stats.c` — про копию прототипа в `main.c` никто не вспомнит, а когда
файлов станет пять, копий станет пять. Поэтому прототипы выносят в
**заголовочный файл** (header) с расширением `.h`, а `#include`
вставляет его текст куда попросят. `stats.h`:

```c
#ifndef STATS_H
#define STATS_H

/* Сумма n элементов массива a. */
int sum(const int *a, int n);

/* Среднее арифметическое; при n == 0 возвращает 0.0. */
double average(const int *a, int n);

#endif
```

Три строчки `#ifndef` / `#define` / `#endif` — **страж включения**
(include guard). `#ifndef STATS_H` читается как «если имя `STATS_H` ещё
не определено». Первый `#include "stats.h"` определяет его и пропускает
содержимое дальше; второй и десятый видят, что `STATS_H` уже есть, и
выбрасывают весь файл. Без стража при двойном включении получишь
«переопределение» на каждый `struct` в заголовке. Имя внутри берут из
имени файла, чтобы не совпало с чужим.

В `main.c` вместо двух прототипов пишем `#include "stats.h"`. Угловые
скобки `<stdio.h>` означают «ищи среди системных заголовков», кавычки
`"stats.h"` — «ищи рядом с моим файлом»; свои заголовки всегда в
кавычках. И — это важно — та же строчка идёт первой **в самом**
`stats.c`.

Зачем включать заголовок в файл, где эти функции и написаны? Чтобы
компилятор сверил объявление с определением. Поменяй в `stats.c` тип
`sum` с `int` на `long`, заголовок не трогай, — и ошибка вылезет сразу:

```text
$ cc -std=c11 -Wall -Wextra main.c stats.c -o prog
stats.c:3:6: error: conflicting types for 'sum'
    3 | long sum(const int *a, int n)
      |      ^
./stats.h:5:5: note: previous declaration is here
    5 | int sum(const int *a, int n);
      |     ^
1 error generated.
```

Без `#include "stats.h"` в `stats.c` это разошлось бы молча и всплыло
странным числом в выводе.

### Раздельная компиляция

`cc main.c stats.c -o prog` каждый раз компилирует оба файла заново.
Флаг `-c` (compile only) останавливает компилятор сразу после перевода
в машинный код: получается **объектный файл** `.o` — кусок программы,
ещё не программа. Собрать их в исполняемый файл можно потом, отдельно:

```text
$ cc -std=c11 -Wall -Wextra -c main.c
$ cc -std=c11 -Wall -Wextra -c stats.c
$ cc main.o stats.o -o prog
$ ./prog
Сумма:   21
Среднее: 4.00
```

Поменял только `stats.c` — пересобирать `main.o` не нужно. На двух
файлах экономия смешная, на двухстах — разница между «пять секунд» и
«пять минут». Но следить руками, что устарело, невозможно. За этим и
нужен `make`.

## Шаг 2. Makefile

`make` — программа, которая читает файл с правилами и пересобирает
только устаревшее. Правило выглядит так:

```
цель: от_чего_зависит
<TAB>команда
```

Отступ перед командой — **настоящий символ табуляции**, не пробелы.
Это первая ошибка каждого новичка: `make` скажет
`missing separator`. Положи рядом со своими файлами `Makefile`
(именно так, с большой буквы, без расширения):

```make
CC     = cc
CFLAGS = -std=c11 -Wall -Wextra -g
OBJ    = main.o stats.o

prog: $(OBJ)
	$(CC) $(OBJ) -o prog

main.o: main.c stats.h
	$(CC) $(CFLAGS) -c main.c

stats.o: stats.c stats.h
	$(CC) $(CFLAGS) -c stats.c

clean:
	rm -f prog $(OBJ)
```

Разбор:

- `CC`, `CFLAGS`, `OBJ` — переменные, обращение к ним `$(CC)`,
  `$(CFLAGS)`. Смысл тот же, что у именованных констант в Си: флаги
  записаны в одном месте.
- `-g` в `CFLAGS` — «положи в программу отладочную информацию»: имена
  переменных и номера строк. Без него отладчик покажет голый ассемблер.
  При разработке держат всегда, на готовой программе убирают.
- `prog: $(OBJ)` — цель `prog` зависит от `main.o` и `stats.o`. Если
  хоть один из них новее, чем `prog`, — выполняем команду ниже.
- `main.o: main.c stats.h` — вот ради чего всё: `main.o` зависит не
  только от своего `.c`, но и от **заголовка**. Правишь `stats.h` —
  пересобираются все, кто его включает.
- `clean` — цель без зависимостей, просто «выполни команду». Файла с
  именем `clean` нет, поэтому `make clean` работает всегда.

Первая цель в файле — цель по умолчанию, поэтому `make` без аргументов
собирает `prog`:

```text
$ make
cc -std=c11 -Wall -Wextra -g -c main.c
cc -std=c11 -Wall -Wextra -g -c stats.c
cc main.o stats.o -o prog
$ ./prog
Сумма:   21
Среднее: 4.00
```

`make` печатает каждую команду перед запуском — видно, что именно он
делает. Теперь запусти второй раз, ничего не меняя:

```text
$ make
make: `prog' is up to date.
```

Ни одной команды: всё свежее. Меняем только `stats.c` и снова `make`:

```text
$ make
cc -std=c11 -Wall -Wextra -g -c stats.c
cc main.o stats.o -o prog
```

`main.c` не трогали — `main.o` не пересобирался. А теперь меняем
заголовок `stats.h`:

```text
$ make
cc -std=c11 -Wall -Wextra -g -c main.c
cc -std=c11 -Wall -Wextra -g -c stats.c
cc main.o stats.o -o prog
```

Пересобралось всё — потому что мы честно прописали зависимость от
`stats.h` в обоих правилах. А `make clean` печатает `rm -f prog
main.o stats.o` и убирает мусор.

Этого «Makefile на десять строк» хватает на годы. Дальше бывают
шаблонные правила (`%.o: %.c`), автоматические переменные (`$@`, `$<`)
и генерация зависимостей флагом `-MMD` — но это уже когда прижмёт.

## Шаг 3. Отладчик: ищем баг в `average`

Пора разобраться с `4.00`. Сумма 21, оценок 5, значит 4.2 — а печатается
4.00. `printf` виноват? Тип не тот? Вместо гаданий запустим программу
под отладчиком.

Отладчик (debugger) умеет остановить программу на нужной строке и
показать значения переменных прямо в этот момент. На macOS штатный
отладчик — `lldb`, на Linux — `gdb`; команды у них разные, идея одна.
Программа уже собрана с `-g`, так что можно начинать:

```text
$ lldb ./prog
(lldb) target create "./prog"
Current executable set to '/Users/me/proj/prog' (x86_64).
(lldb) b stats.c:16
Breakpoint 1: where = prog`average + 46 at stats.c:16:12, address = 0x00000001000005de
(lldb) run
Сумма:   21
Process 68496 launched: '/Users/me/proj/prog' (x86_64)
Process 68496 stopped
* thread #1, queue = 'com.apple.main-thread', stop reason = breakpoint 1.1
    frame #0: 0x00000001000005de prog`average(a=0x00007ff7bfefe620, n=5) at stats.c:16:12
   13  	    if (n == 0)
   14  	        return 0.0;
   15  	    int s = sum(a, n);
-> 16  	    return s / n;
    	           ^
   17  	}
Target 0: (prog) stopped.
(lldb) p s
(int) 21
(lldb) p n
(int) 5
(lldb) p s / n
(int) 4
(lldb) p (double) s / n
(double) 4.2000000000000002
(lldb) bt
* thread #1, queue = 'com.apple.main-thread', stop reason = breakpoint 1.1
  * frame #0: 0x00000001000005de prog`average(a=0x00007ff7bfefe620, n=5) at stats.c:16:12
    frame #1: 0x000000010000052b prog`main at main.c:10:38
    frame #2: 0x00007ff804aa4b28 dyld`start + 3240
(lldb) c
Среднее: 4.00
Process 68496 resuming
Process 68496 exited with status = 0 (0x00000000)
(lldb) quit
```

Номер процесса и адреса у тебя будут свои — это нормально. Что тут
произошло:

- `b stats.c:16` — `b` от **breakpoint**, точка останова: «останови
  программу перед выполнением строки 16 файла `stats.c`». Можно и по
  имени функции: `b average`.
- `run` — запуск. Программа успела напечатать «Сумма: 21» и замерла на
  нашей строке. Отладчик показал кусок исходника и стрелкой `->`
  отметил строку, которая **ещё не выполнена**.
- `p s` — от **print**: напечатать выражение. Ответ `(int) 21` —
  отладчик показывает и тип, и значение. Печатать можно не только
  переменные: `p s / n` даёт `(int) 4`. Вот и баг. Оба операнда —
  `int`, значит деление целочисленное, дробная часть выброшена **до**
  того, как результат стал `double` (главы 2 и 4; в чужой функции
  такое глазами ловится плохо). `p (double) s / n` проверяет гипотезу, не
  трогая код: `4.2000000000000002`.
- `bt` — от **backtrace**, стек вызовов: кто кого позвал. Читается
  снизу вверх: система запустила `start`, тот вызвал `main` (строка 10
  файла `main.c`), а `main` вызвал `average`. Когда программа падает,
  `bt` — первое, что надо набрать.
- `c` — от **continue**, «беги дальше»; `quit` — выйти.

Ещё три команды, которые понадобятся сразу: `n` (**next**) — выполнить
одну строку и снова остановиться; `s` (**step**) — то же, но зайти
внутрь вызванной функции; `finish` — доработать текущую функцию до
конца и остановиться у того, кто её вызвал.

Чиним `stats.c`:

```c
double average(const int *a, int n)
{
    if (n == 0)
        return 0.0;
    int s = sum(a, n);
    return (double) s / n;
}
```

`(double) s` — приведение типа: «считай `s` вещественным». Достаточно
привести **один** операнд, второй Си повысит сам.

```text
$ make
cc -std=c11 -Wall -Wextra -g -c stats.c
cc main.o stats.o -o prog
$ ./prog
Сумма:   21
Среднее: 4.20
```

Обрати внимание: `make` пересобрал только `stats.o`. Всё сходится.

## Шаг 4. Файлы: `fopen`, `fgets`, `fclose`

Пока всё, что печатали наши программы, исчезало при закрытии терминала.
Файл — это способ сохранить.

Работа с файлом всегда идёт по одной схеме: **открыть — работать —
закрыть**. Открывает `fopen` из `<stdio.h>`:

```c
FILE *fopen(const char *path, const char *mode);
```

`path` — имя файла, `mode` — строка режима: `"r"` — читать (файла нет
→ ошибка), `"w"` — писать (файл создаётся, а существующий **обнуляется**),
`"a"` — дописывать в конец. Возвращает `FILE *` — указатель на
служебную структуру, которую дальше передают всем остальным функциям.
Если открыть не удалось, возвращает `NULL`.

Пишут в файл функцией `fprintf` — это `printf`, которому первым
аргументом сказали, **куда** печатать; остальное те же `%d`, `%s`,
`\n`:

```c
FILE *out = fopen("scores.txt", "w");
fprintf(out, "anna 120\n");
fclose(out);
```

`fclose(out)` закрывает файл и, что важнее, дописывает на диск то, что
ещё лежало в буфере. Забудешь `fclose` — рискуешь получить пустой файл.

Читать начнём с готового файла — сделаем его прямо в терминале, чтобы
не отвлекаться:

```text
$ printf 'anna 120\nboris 95\nvika 143\n' > scores.txt
$ cat scores.txt
anna 120
boris 95
vika 143
```

Наивная читалка, `read1.c`:

```c
#include <stdio.h>

int main(void)
{
    FILE *f = fopen("scores.txt", "r");
    char line[128];

    while (fgets(line, sizeof line, f) != NULL)
        printf("прочитал: %s", line);

    fclose(f);
    return 0;
}
```

`fgets(buf, size, f)` — тот самый `fgets`, которым мы всю книгу читали
строки с клавиатуры, только последним аргументом теперь не `stdin`, а
наш файл. Читает не больше `size - 1` символов, дописывает `'\0'` и
возвращает `buf`, а на конце файла — `NULL`.

```text
$ cc -std=c11 -Wall -Wextra -O2 read1.c -o read1
$ ./read1
прочитал: anna 120
прочитал: boris 95
прочитал: vika 143
```

Работает. Теперь удали файл (`rm scores.txt`) и запусти снова:

```text
$ ./read1
$ echo $?
139
```

Ни строчки вывода и код возврата 139. Программа упала: 139 — это
128 + 11, а сигнал 11 — `SIGSEGV`, обращение по неверному адресу.
Причина: `fopen` вернул `NULL`, и `fgets` полез читать по нулевому
адресу. **Результат `fopen` проверяют всегда** — это не паранойя, файла
может не быть, к нему может не быть прав, диск может быть переполнен.

Вторая ловушка видна, если вернуть файл на место, добавить проверку
`fopen` и напечатать строку в квадратных скобках —
`printf("строка: [%s]\n", line)`:

```text
$ ./read2
строка: [anna 120
]
строка: [boris 95
]
строка: [vika 143
]
```

`fgets` оставляет в буфере **символ перевода строки**. Если строку
дальше сравнивать или склеивать, этот `'\n'` всё испортит. Срезают его
так:

```c
size_t len = strlen(line);
if (len > 0 && line[len - 1] == '\n')
    line[len - 1] = '\0';
```

Проверка `len > 0` обязательна: без неё на пустом буфере `line[-1]` —
выход за границу.

Итоговая программа — `code/18-files.c`. Она пишет файл, читает его
обратно, разбирает каждую строку на имя и число и считает сумму:

```c
/* 18-files.c — запись и чтение текстового файла.
   Пишем таблицу рекордов, читаем её обратно построчно и считаем сумму.
   Каждый вызов, который может провалиться, проверяем. */
#include <stdio.h>
#include <string.h>

int main(void)
{
    const char *path = "scores.txt";

    /* --- 1. Пишем файл --- */
    FILE *out = fopen(path, "w");
    if (out == NULL) {
        printf("Не могу открыть %s на запись\n", path);
        return 1;
    }

    fprintf(out, "anna 120\n");
    fprintf(out, "boris 95\n");
    fprintf(out, "vika 143\n");

    if (fclose(out) != 0) {
        printf("Ошибка при закрытии %s\n", path);
        return 1;
    }
    printf("Записал 3 строки в %s\n", path);

    /* --- 2. Читаем файл обратно --- */
    FILE *in = fopen(path, "r");
    if (in == NULL) {
        printf("Не могу открыть %s на чтение\n", path);
        return 1;
    }

    char line[128];
    int players = 0;
    int total = 0;

    while (fgets(line, sizeof line, in) != NULL) {
        size_t len = strlen(line);
        if (len > 0 && line[len - 1] == '\n')
            line[len - 1] = '\0';       /* срезаем перевод строки */

        char name[64];
        int score;
        if (sscanf(line, "%63s %d", name, &score) == 2) {
            players++;
            total += score;
            printf("%d. %s — %d очков\n", players, name, score);
        } else {
            printf("не разобрал строку: \"%s\"\n", line);
        }
    }

    if (ferror(in))
        printf("Чтение оборвалось на ошибке\n");
    fclose(in);

    if (players > 0)
        printf("Игроков: %d, всего очков: %d\n", players, total);

    remove(path);                       /* убираем за собой */
    return 0;
}
```

Что нового:

- `sscanf(line, "%63s %d", name, &score)` — `scanf`, который читает не
  с клавиатуры, а из строки в памяти. Возвращает число успешно
  разобранных значений, поэтому `== 2` значит «нашлись и имя, и
  число». `%63s` с числом — ограничитель длины: не больше 63 символов
  плюс `'\0'` в буфер на 64. Без числа `%s` радостно вылезет за
  границу массива на длинном имени.
- `ferror(in)` — «чтение закончилось из-за ошибки, а не из-за конца
  файла?». `fgets` в обоих случаях возвращает `NULL`, и различить их
  можно только так (или через `feof`).
- `remove(path)` — удалить файл. Здесь он нужен, чтобы программа
  убирала за собой и её можно было запускать сколько угодно раз.
  Закомментируй эту строку, если хочешь посмотреть на `scores.txt`
  своими глазами.

```text
$ cc -std=c11 -Wall -Wextra -O2 code/18-files.c -o files
$ ./files
Записал 3 строки в scores.txt
1. anna — 120 очков
2. boris — 95 очков
3. vika — 143 очков
Игроков: 3, всего очков: 358
```

Имена здесь латиницей не случайно: если выравнивать колонки по ширине
(`%-8s`), ширина считается в **байтах**, а кириллическая буква в UTF-8
занимает два — таблица поедет. Та же история, что с посимвольной
обработкой русских слов в главе 10.

## Стандарты и платформы, коротко

Всю книгу мы собирали с `-std=c11` — стандартом 2011 года: он давно и
всюду поддержан. После него вышли ещё два. **C17** (он же C18) — только
правки и уточнения, новых возможностей нет; переключение с C11 на C17
обычно вообще ничего не меняет. **C23** — первый за долгое время
стандарт с заметными новинками: `bool`, `true` и `false` без
`#include <stdbool.h>`, `nullptr` вместо `NULL`, `constexpr` для
настоящих констант, двоичные литералы `0b1011`.

Что понимает твой компилятор, покажет макрос `__STDC_VERSION__` —
номер стандарта в виде «год и месяц». Положи в `std.c` обычную
программу с единственной строкой в `main`:

```c
printf("__STDC_VERSION__ = %ld\n", __STDC_VERSION__);
```

```text
$ cc -std=c11 std.c -o std && ./std
__STDC_VERSION__ = 201112
$ cc -std=c17 std.c -o std && ./std
__STDC_VERSION__ = 201710
$ cc -std=c23 std.c -o std && ./std
__STDC_VERSION__ = 202311
```

Пиши на C11, пока не появилась конкретная причина переехать, и
проверяй `-std=`, прежде чем копировать чужой свежий код: программа с
`nullptr` под `-std=c11` просто не соберётся.

Про платформы. Всё, что мы писали, — чистый Си, кроме «Змейки»:
`termios.h`, `tcsetattr`, `usleep` — это POSIX (macOS, Linux и прочие
Unix-подобные). На Windows этих заголовков нет, там свой API
(`conio.h`, `_kbhit`, `_getch`, `Sleep`). Обычный приём — развилка на
этапе компиляции: компилятор сам определяет макросы под текущую
систему (`_WIN32` на Windows, `__APPLE__` на macOS, `__linux__` на
Linux), а препроцессор выбирает нужный кусок и прячет его за своей
функцией вроде `sleep_ms`, чтобы остального кода это не касалось.

## Частые ошибки

- **Тело функции в `.h`.** Заголовок вставляется в каждый `.c`,
  который его включил. Определение функции окажется в двух объектных
  файлах, и компоновщик скажет `duplicate symbol`. В `.h` — только
  объявления, `struct`, `#define`.
- **Забыт страж включения.** Работает, пока заголовок включён один раз.
  Как только он попадёт в программу дважды — посыплются
  «redefinition».
- **Пробелы вместо табуляции в `Makefile`.** `make` отвечает
  `missing separator`. Проверь, что редактор не «улучшил» твой TAB.
- **Забыта зависимость от `.h` в `Makefile`.** Правишь заголовок,
  `make` говорит «up to date», программа собрана из старых `.o` и ведёт
  себя необъяснимо. Правило: у каждого `.o` в зависимостях перечислены
  все заголовки, которые он включает.
- **Отладка без `-g`.** `lldb` запустится, но покажет адреса вместо
  имён и строк. Всегда собирай отладочную версию с `-g`.
- **`fopen` без проверки на `NULL`.** Самая частая ошибка при работе с
  файлами и, как мы видели, сразу падение.
- **Забытый `fclose`.** Данные остаются в буфере, файл на диске
  пустой или обрезанный.
- **`'\n'` в конце строки от `fgets`.** Забудешь срезать — сравнения
  строк перестанут совпадать, а вывод поедет.

## Упражнения

1. Разбей на файлы что-нибудь из книги. Возьми `code/08-bubble.c` или
   `code/11-stack.c`, вынеси алгоритм в `sort.c`/`sort.h` (или
   `stack.c`/`stack.h`), оставь в `main.c` только ввод и вывод и собери
   через `Makefile`.
2. Добавь в `Makefile` цель `run`, которая сначала собирает `prog`, а
   потом его запускает (подсказка: цель `run` должна зависеть от
   `prog`), и цель `debug`, собирающую с `-fsanitize=address,undefined`.
3. Возьми программу с багом — например, намеренно испорти границу цикла
   в бинарном поиске из главы 7 — и найди ошибку **только** отладчиком,
   без единого `printf`. Поставь точку останова внутри цикла и смотри,
   как меняются `lo`, `hi`, `mid`.
4. Переделай `code/18-files.c` так, чтобы имя файла бралось из
   командной строки: `int main(int argc, char *argv[])`, файл —
   `argv[1]`. Не забудь проверить `argc >= 2`, иначе `argv[1]` окажется
   `NULL`.
5. Допиши в «Угадай число» (глава 12) таблицу рекордов: после победы
   программа дописывает число попыток в `records.txt` режимом `"a"`, а
   при старте читает файл и печатает лучший результат.
6. Напиши программу `wc`: читает файл, имя которого дано в командной
   строке, и печатает число строк, слов и символов. Слова считай так
   же, как в главе 10.
