# Глава 7. Поиск: линейный и бинарный

Самая частая работа с массивом — что-то в нём **найти**. Есть ли число
15 в списке? На каком оно месте? В этой главе мы решим эту задачу двумя
способами. Сначала в лоб — пройдём весь массив подряд (линейный поиск).
Потом — хитро, вдвое сужая зону поиска на каждом шаге (бинарный поиск).
Заодно увидим, почему второй способ на больших данных в тысячи раз
быстрее, и какую цену за это приходится платить.

## Что мы сделаем

Напишем две функции поиска. Обе получают массив, его длину и искомое
число, а возвращают **индекс** найденного элемента или `-1`, если его
нет. Линейный поиск работает на любом массиве. Бинарный — только на
**отсортированном**, зато молниеносно. К концу главы ты будешь понимать,
когда какой брать и почему.

## Разбираем задачу руками

Представь список номеров шкафчиков, выданных на руки:

```text
индекс:  0    1    2    3    4    5    6
число:  17    4   42    8   15   23   16
```

Вопрос: на каком месте стоит число 15? Глазами ты просто пробегаешь
слева направо: 17 — не то, 4 — не то, 42 — не то, 8 — не то, 15 — есть!
Это позиция (индекс) 4. Именно так и работает линейный поиск: проверяй
элементы по очереди, пока не наткнёшься на нужный.

А если числа нет — например, ищем 99? Тогда придётся дойти до самого
конца, проверить все семь штук и только тогда сказать «нету». Запомни
этот момент: когда элемента нет, линейный поиск всегда проверяет **весь**
массив.

## Шаг 1. Наивный линейный поиск прямо в main

Сначала без функции, чтобы увидеть саму идею. Пройдём массив циклом и,
как только встретим нужное число, напечатаем его позицию.

```c
#include <stdio.h>

int main(void)
{
    int a[] = {17, 4, 42, 8, 15, 23, 16};
    int n = (int)(sizeof a / sizeof a[0]);
    int target = 15;

    for (int i = 0; i < n; i++) {
        if (a[i] == target) {
            printf("Найдено на позиции %d\n", i);
        }
    }
    return 0;
}
```

Здесь почти всё знакомо, но есть одна новая полезная конструкция.

- `int a[] = {17, 4, ...};` — массив без явного размера в скобках.
  Компилятор сам посчитает, что элементов семь (см. главу 3).
- `sizeof a / sizeof a[0]` — так узнают **длину массива**. `sizeof a` —
  размер всего массива в байтах (у нас `int` занимает 4 байта, значит,
  7 чисел по 4 байта = 28). `sizeof a[0]`
  — размер одного элемента (4 байта). Поделили — получили **число
  элементов**: 28 / 4 = 7. Это надёжнее, чем писать 7 руками: поменяешь
  список — длина пересчитается сама.
- `(int)(...)` — `sizeof` выдаёт значение специального беззнакового типа
  `size_t`. Чтобы хранить длину в обычном `int` без предупреждений
  компилятора, мы приводим результат к `int` (приведение типа из главы 3).
- `target` — англ. «цель», искомое число.
- Внутри цикла сравниваем каждый `a[i]` с `target` через `==` и при
  совпадении печатаем индекс.

Собираем и запускаем:

```text
Найдено на позиции 4
```

Работает. Но у этой наивной версии есть три проблемы, и сейчас мы их
вытащим на свет.

## Шаг 2. Что не так с наивной версией

**Проблема 1: цикл не останавливается.** Мы нашли число на позиции 4, но
цикл всё равно добегает до конца массива. На семи элементах это пустяк, а
на миллионе — впустую потраченное время. Нашёл — выходи.

**Проблема 2: нет ответа «не найдено».** Поищем число 99 — программа
просто промолчит, ничего не напечатает. Это плохо: «ничего не вывели» и
«не нашли» — разные вещи, но выглядят одинаково.

**Проблема 3: поиск зашит в `main`.** Захочешь искать в другом массиве —
придётся копировать весь цикл. Логику поиска надо вынести в **функцию**,
чтобы вызывать её сколько угодно раз.

Чинить будем все три разом: завернём поиск в функцию, которая
**возвращает** индекс найденного элемента, а если не нашла — возвращает
`-1`. Почему именно `-1`? Потому что настоящий индекс всегда `0` или
больше. Значит, `-1` не спутать с настоящей позицией — это удобный знак
«такого нет».

## Шаг 3. Линейный поиск как функция

```c
int linear_search(const int a[], int n, int target)
{
    for (int i = 0; i < n; i++) {
        if (a[i] == target) {
            return i;       /* нашли — сразу отдаём индекс */
        }
    }
    return -1;              /* дошли до конца и не встретили target */
}
```

Разбор сигнатуры `int linear_search(const int a[], int n, int target)`:

- первый `int` — тип возвращаемого значения. Функция вернёт индекс
  (целое число) или `-1`, тоже целое.
- `linear_search` — имя, придумали сами. От англ. *linear* — «линейный»,
  то есть идём по прямой, элемент за элементом.
- `const int a[]` — параметр-массив. Когда передаёшь массив в функцию,
  туда уходит не копия элементов, а **адрес его начала** (помнишь из
  главы 3: имя массива превращается в адрес). Запись `int a[]` и означает «сюда придёт
  массив целых». А слово **`const`** — обещание: «внутри функции я этот
  массив **менять не буду**, только читаю». Это новое для нас. `const`
  (от *constant* — постоянный) защищает данные: если ты случайно
  напишешь `a[i] = 5`, компилятор остановит тебя с ошибкой. Для поиска
  это в самый раз — искать значит читать, а не портить.
- `int n` — сколько элементов в массиве. Массив сам по себе **не знает**
  свою длину (внутри функции трюк с `sizeof` уже не сработает — там `a`
  это адрес, а не весь массив), поэтому длину передают отдельным
  параметром. Это стандартный приём в Си.
- `int target` — что ищем.

Теперь самое важное — **`return` внутри цикла**:

- `return i;` — как только нашли совпадение, функция немедленно
  заканчивается и **отдаёт наружу** `i`. Цикл при этом обрывается на
  месте — `return` выходит сразу из всей функции, а не только из цикла.
  Это решает проблему 1: лишних шагов нет.
- `return -1;` — эта строка стоит **после** цикла. До неё дойдёт
  выполнение, только если цикл отработал целиком и ни разу не сделал
  `return i`. То есть мы проверили все элементы и не нашли. Значит —
  `-1`. Это решает проблему 2.

## Полная программа: линейный поиск

Файл `code/07-linear.c`:

```c
#include <stdio.h>

/* Линейный поиск: ищем значение target в первых n элементах массива a.
   Возвращаем индекс первого совпадения или -1, если ничего не нашли. */
int linear_search(const int a[], int n, int target)
{
    for (int i = 0; i < n; i++) {
        if (a[i] == target) {
            return i;       /* нашли — сразу отдаём индекс */
        }
    }
    return -1;              /* дошли до конца и не встретили target */
}

int main(void)
{
    int a[] = {17, 4, 42, 8, 15, 23, 16};
    int n = (int)(sizeof a / sizeof a[0]);

    int target = 15;
    int index = linear_search(a, n, target);

    if (index != -1) {
        printf("Число %d найдено на позиции %d\n", target, index);
    } else {
        printf("Число %d в массиве не найдено\n", target);
    }

    int missing = 99;
    int index2 = linear_search(a, n, missing);
    if (index2 != -1) {
        printf("Число %d найдено на позиции %d\n", missing, index2);
    } else {
        printf("Число %d в массиве не найдено\n", missing);
    }

    return 0;
}
```

В `main` мы вызываем функцию и **сохраняем** её ответ в переменную
`index`. Дальше одной проверкой `if (index != -1)` решаем, что печатать:
позицию или «не найдено». Так результат функции используется по-взрослому
— сначала получили число, потом разобрались, что оно значит.

Запуск:

```text
Число 15 найдено на позиции 4
Число 99 в массиве не найдено
```

Оба случая обработаны: и когда число есть, и когда его нет.

## Линейный поиск медленный — и вот почему

Линейный поиск прост и работает на **любом** массиве, хоть как
перемешанном. Но у него есть слабое место. Прикинем, сколько сравнений
`a[i] == target` он делает. Число это зависит от того, где лежит искомое,
поэтому про скорость алгоритма говорят тремя словами:

- **лучший случай** — самый удачный вход. Искомое стоит первым, хватает
  одного сравнения;
- **худший случай** — самый неудачный вход. Искомого нет или оно стоит
  последним, и придётся проверить **все** `n` элементов;
- **средний случай** — сколько выходит в среднем, если искомое с равным
  шансом может оказаться на любом из `n` мест. На первом месте — одно
  сравнение, на втором — два, ..., на последнем — `n`. Среднее
  `(1 + 2 + ... + n) / n = (n + 1) / 2`, то есть примерно половина
  массива. Для наших семи чисел: `(1 + 2 + ... + 7) / 7 = 28 / 7 = 4`.

Лучший случай почти ничего не говорит: повезти может любому алгоритму.
Обычно смотрят на худший — это гарантия «хуже не будет»:

- массив из 10 элементов — до 10 проверок;
- из 1000 — до 1000 проверок;
- из 1 000 000 — до миллиона проверок.

Сколько элементов — столько и работы. Растёт массив в тысячу раз — растёт
и время поиска в тысячу раз (и в худшем, и в среднем случае). Для
небольших списков это незаметно. Но
представь телефонный справочник на миллионы записей, где ищут постоянно —
перебирать всё подряд каждый раз слишком расточительно.

Хорошая новость: если массив **отсортирован**, искать можно несравнимо
быстрее. Этим и займёмся.

## Шаг 4. Идея бинарного поиска — руками

Ты наверняка так искал слово в бумажном словаре. Не листаешь с первой
страницы подряд! Открываешь примерно посередине, смотришь, в какую
половину попадает твоё слово, и **отбрасываешь вторую половину целиком**.
Потом повторяешь с оставшейся половиной. Каждый раз книга «худеет» вдвое
— и нужная страница находится за считанные шаги.

Это и есть **бинарный поиск** (binary — «двоичный», «на две части»). Но у
него жёсткое условие: он работает **только на отсортированном массиве**.
Иначе «отбросить половину» нельзя — без порядка непонятно, в какой стороне
искать.

Возьмём отсортированный по возрастанию массив и поищем в нём число 7:

```text
индекс:  0    1    2    3    4    5
число:   1    3    5    7    9   11
```

Заведём две границы зоны поиска: `low` (левая, начало) и `high` (правая,
конец). В начале зона — весь массив: `low = 0`, `high = 5`.

**Шаг A.** Середина: `mid = (0 + 5) / 2 = 2`. В середине стоит `a[2] = 5`.
Это **меньше** семёрки. Раз массив отсортирован, всё, что левее середины,
тоже меньше 7 — значит, левая половина и сама середина нам не нужны.
Сдвигаем левую границу за середину: `low = mid + 1 = 3`. Зона сузилась до
индексов 3..5.

**Шаг B.** Середина новой зоны: `mid = (3 + 5) / 2 = 4`. Там `a[4] = 9`.
Это **больше** семёрки. Значит, всё, что правее (и сама девятка), нам не
подходит. Сдвигаем правую границу: `high = mid - 1 = 3`. Зона — только
индекс 3.

**Шаг C.** `mid = (3 + 3) / 2 = 3`. Там `a[3] = 7`. **Совпало!** Ответ —
позиция 3.

Три шага вместо потенциальных шести. На маленьком массиве выигрыш скромный,
но он растёт стремительно с размером — скоро увидим, насколько.

## Шаг 5. Почему `mid = low + (high - low) / 2`, а не `(low + high) / 2`

Казалось бы, середину проще считать как `(low + high) / 2` — и
математически это то же самое. Но в реальном коде есть ловушка.

`low` и `high` — переменные типа `int`. У `int` есть **потолок**:
2 147 483 647 (об этом упоминали в главе 2). Если обе границы заехали
близко к потолку, их **сумма** `low + high` его перепрыгнет — это
**переполнение** (overflow). В Си переполнение знакового целого — не
«число просто заворачивается по кругу», а **неопределённое поведение**:
стандарт не обещает ничего, компилятор вправе выдать любой результат. На
практике обычно получается отрицательное число, и `mid` указывает
в никуда.

Не будем верить на слово — посчитаем середину обоими способами на числах,
близких к потолку. Файл `overflow.c`:

```c
#include <stdio.h>

int main(void)
{
    int low  = 1500000000;
    int high = 2000000000;

    int safe  = low + (high - low) / 2;   /* так правильно */
    int naive = (low + high) / 2;         /* а вот тут беда */

    printf("low + (high - low) / 2 = %d\n", safe);
    printf("(low + high) / 2       = %d\n", naive);
    return 0;
}
```

Собираем обычным образом и запускаем:

```text
cc -std=c11 -Wall -Wextra -O2 overflow.c -o overflow
./overflow
low + (high - low) / 2 = 1750000000
(low + high) / 2       = -397483648
```

Правильная середина — 1 750 000 000. А «наивная» формула выдала **минус**
397 миллионов. Индексом такое число быть не может: `a[-397483648]` — это
обращение к чужой памяти и почти наверняка падение программы.

Компилятор с обычными флагами промолчал — ни одного предупреждения. Зато
не промолчит санитайзер неопределённого поведения, знакомый по главе 4.
Пересобираем с `-fsanitize=undefined`:

```text
cc -std=c11 -Wall -Wextra -g -fsanitize=undefined overflow.c -o ovf-san
./ovf-san
overflow.c:9:22: runtime error: signed integer overflow: 1500000000 +
2000000000 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior overflow.c:9:22
low + (high - low) / 2 = 1750000000
(low + high) / 2       = -397483648
```

(Первая строка отчёта на экране длинная, здесь она перенесена.)
Программа сама показала пальцем: строка 9, столбец 22 — там, где стоит
`+` в `(low + high)`. «Signed integer overflow: сумма 1500000000 +
2000000000 не представима в типе int». Строка `SUMMARY` — итог: сколько
и где нашлось неопределённого поведения. Отчёт санитайзер печатает в
момент ошибки, а программа после этого работает дальше, поэтому оба
наших `printf` идут следом.

А теперь про масштаб: **когда это случается в жизни?**
Переполнение наступает, только если `low + high` превысит 2 147 483 647.
Обе границы не больше `n - 1`, значит, их сумма не больше
`(n - 1) + (n - 1) = 2n - 2`. Чтобы она перевалила за 2 147 483 647,
нужно `n` не меньше 1 073 741 825 (два в тридцатой степени плюс
один) — чуть больше миллиарда элементов. Массив `int` такого размера
занимает около **четырёх гигабайт** памяти. На учебных примерах ты этого не увидишь
никогда.

Так зачем возиться? Потому что такие массивы бывают — в базах данных, в
поисковых индексах, в обработке логов. Ровно на этом когда-то обожглись
в стандартной библиотеке Java: её `Arrays.binarySearch` складывала
`low + high` и лишь потом делила пополам (сдвигом `>> 1`, что то же
деление на 2). На массиве больше миллиарда элементов сумма
переполнялась. Сообщение об ошибке завели в 2004 году, исправили в 2006-м,
и в том же 2006-м о ней громко написал один из авторов этого кода,
Джошуа Блох. Безопасная форма не стоит ни строчки лишнего кода, а
привычка однажды спасёт.

Запись `low + (high - low) / 2` даёт **то же самое** значение середины, но
устроена безопасно:

- `high - low` — это ширина зоны. Внутри цикла обе границы лежат между
  `0` и `n - 1`, и `low <= high`, поэтому разность не бывает меньше нуля
  и больше `n - 1`, переполниться ей негде;
- делим её пополам — `(high - low) / 2`, это половина ширины;
- прибавляем к `low` — получаем точку ровно посередине между границами.

Сумма двух больших чисел нигде не возникает, потолок не пробивается.
Привыкай писать середину именно так — это стандартная защита, её ждут от
тебя в любом нормальном коде.

## Полная программа: бинарный поиск

Файл `code/07-binary.c`:

```c
#include <stdio.h>

/* Бинарный поиск. ВАЖНО: массив a ДОЛЖЕН быть отсортирован по
   возрастанию. Ищем target, возвращаем его индекс или -1.
   Если target встречается несколько раз — вернётся индекс одного
   из совпадений, не обязательно первого. */
int binary_search(const int a[], int n, int target)
{
    int low = 0;            /* левая граница диапазона поиска */
    int high = n - 1;       /* правая граница диапазона поиска */

    while (low <= high) {
        int mid = low + (high - low) / 2;   /* середина без переполнения */

        if (a[mid] == target) {
            return mid;                     /* попали точно в середину */
        } else if (a[mid] < target) {
            low = mid + 1;                  /* target правее середины */
        } else {
            high = mid - 1;                 /* target левее середины */
        }
    }
    return -1;                              /* диапазон схлопнулся — нет */
}

int main(void)
{
    /* Массив уже отсортирован по возрастанию. */
    int a[] = {1, 3, 5, 7, 9, 11};
    int n = (int)(sizeof a / sizeof a[0]);

    int target = 7;
    int index = binary_search(a, n, target);

    if (index != -1) {
        printf("Число %d найдено на позиции %d\n", target, index);
    } else {
        printf("Число %d в массиве не найдено\n", target);
    }

    int missing = 8;
    int index2 = binary_search(a, n, missing);
    if (index2 != -1) {
        printf("Число %d найдено на позиции %d\n", missing, index2);
    } else {
        printf("Число %d в массиве не найдено\n", missing);
    }

    return 0;
}
```

Разбор тела функции:

- `int low = 0;` и `int high = n - 1;` — границы зоны поиска. В начале
  она охватывает весь массив: от первого индекса `0` до последнего
  `n - 1`. (Последний индекс именно `n - 1`, а не `n` — нумерация с нуля,
  см. главу 3.)
- `while (low <= high)` — повторяем, **пока зона не пуста**. Условие
  `low <= high` означает «в зоне ещё есть хотя бы один элемент». Как
  только границы перехлестнутся (`low` станет больше `high`), искать
  негде — выходим. Знак `<=`, а не `<`, важен: при `low == high` в зоне
  остался ровно один элемент, и его тоже надо проверить.
- `int mid = low + (high - low) / 2;` — середина зоны, посчитанная
  безопасно (только что разобрали почему).
- `if (a[mid] == target) return mid;` — повезло, в середине ровно то, что
  ищем. Отдаём индекс `mid`.
- `else if (a[mid] < target)` — в середине число **меньше** искомого. Раз
  массив отсортирован по возрастанию, искомое (если оно есть) лежит
  **правее**. Отрезаем левую половину: `low = mid + 1`. Прибавляем 1,
  потому что саму середину уже проверили — повторять её незачем.
- `else` — остаётся случай «в середине число **больше** искомого». Тогда
  искомое лежит **левее**. Отрезаем правую половину: `high = mid - 1`.
- `return -1;` — если цикл завершился сам (границы сошлись), числа нет.

Обрати внимание: `mid + 1` и `mid - 1` — не прихоть. Если бы мы писали
`low = mid` (без +1), то в зоне из двух элементов середина не двигалась бы,
и цикл крутился бы **вечно**. Сдвиг через середину гарантирует, что зона
на каждом шаге реально уменьшается.

Запуск:

```text
Число 7 найдено на позиции 3
Число 8 в массиве не найдено
```

Семёрку нашли на позиции 3 — ровно как считали руками. А восьмёрки в
массиве нет (там только нечётные), и функция честно вернула `-1`.

## Как это работает: трассировка по шагам

Пройдём `binary_search(a, 6, 7)` по строчкам, выписывая значения границ.
Массив: `1 3 5 7 9 11`, индексы `0..5`.

```text
Старт:   low=0, high=5
Шаг 1:   mid = 0 + (5-0)/2 = 2   a[2]=5   5 < 7  -> low = 3
Шаг 2:   mid = 3 + (5-3)/2 = 4   a[4]=9   9 > 7  -> high = 3
Шаг 3:   mid = 3 + (3-3)/2 = 3   a[3]=7   7 == 7 -> return 3
```

Зона поиска ужималась так: сначала весь массив (6 элементов), потом
индексы 3..5 (3 элемента), потом только индекс 3 (1 элемент) — и попадание.
Каждый шаг выбрасывал примерно половину оставшихся вариантов.

А теперь трассировка для отсутствующего числа `8`:

```text
Старт:   low=0, high=5
Шаг 1:   mid = 2   a[2]=5   5 < 8  -> low = 3
Шаг 2:   mid = 4   a[4]=9   9 > 8  -> high = 3
Шаг 3:   mid = 3   a[3]=7   7 < 8  -> low = 4
Теперь low=4, high=3  ->  low > high  ->  цикл кончился  ->  return -1
```

Границы перехлестнулись (`low` обогнал `high`) — это и есть сигнал «зона
пуста, числа нет».

## Краевые случаи: проверяем функцию на прочность

Алгоритм на красивом примере работает почти у всех. Ломается он на
**краях**: пустой массив, массив из одного элемента, искомое в самом
начале или в самом конце, повторяющиеся числа. Именно там живут баги, и
именно это спрашивают на собеседовании. Прогоним нашу функцию через все
такие случаи разом.

Файл `code/07-binary-edge.c` — та же `binary_search`, но `main` в нём
устраивает ей допрос:

```c
int main(void)
{
    int empty[1] = {0};        /* массив есть, но искать будем в нуле */
    int one[] = {5};
    int a[] = {1, 3, 5, 7, 9, 11};
    int dup[] = {2, 4, 4, 4, 4, 7, 9};

    printf("пустой массив, ищем 5:        %d\n",
           binary_search(empty, 0, 5));
    printf("один элемент {5}, ищем 5:     %d\n",
           binary_search(one, 1, 5));
    printf("один элемент {5}, ищем 4:     %d\n",
           binary_search(one, 1, 4));
    printf("1 3 5 7 9 11, ищем 1:         %d\n",
           binary_search(a, 6, 1));
    printf("1 3 5 7 9 11, ищем 11:        %d\n",
           binary_search(a, 6, 11));
    printf("1 3 5 7 9 11, ищем 0:         %d\n",
           binary_search(a, 6, 0));
    printf("1 3 5 7 9 11, ищем 12:        %d\n",
           binary_search(a, 6, 12));
    printf("2 4 4 4 4 7 9, ищем 4:        %d\n",
           binary_search(dup, 7, 4));

    /* А теперь запретный приём: неотсортированный массив.
       Каждое число в нём ЕСТЬ, но бинарный поиск это не спасёт. */
    int mess[] = {17, 4, 42, 8, 15, 23, 16};
    int m = (int)(sizeof mess / sizeof mess[0]);

    printf("\nнеотсортированный 17 4 42 8 15 23 16:\n");
    for (int i = 0; i < m; i++) {
        printf("  ищем %2d (лежит на %d) -> %d\n",
               mess[i], i, binary_search(mess, m, mess[i]));
    }

    return 0;
}
```

Пара слов про `empty`. Массив нулевой длины в Си объявить нельзя, поэтому
мы завели массив из одного элемента, а функции передали `n = 0` —
«элементов ноль». Функция обязана честно ответить «не нашла», ни разу не
заглянув в память.

Запускаем:

```text
cc -std=c11 -Wall -Wextra -O2 07-binary-edge.c -o 07-binary-edge
./07-binary-edge
пустой массив, ищем 5:        -1
один элемент {5}, ищем 5:     0
один элемент {5}, ищем 4:     -1
1 3 5 7 9 11, ищем 1:         0
1 3 5 7 9 11, ищем 11:        5
1 3 5 7 9 11, ищем 0:         -1
1 3 5 7 9 11, ищем 12:        -1
2 4 4 4 4 7 9, ищем 4:        3

неотсортированный 17 4 42 8 15 23 16:
  ищем 17 (лежит на 0) -> -1
  ищем  4 (лежит на 1) -> 1
  ищем 42 (лежит на 2) -> -1
  ищем  8 (лежит на 3) -> 3
  ищем 15 (лежит на 4) -> 4
  ищем 23 (лежит на 5) -> 5
  ищем 16 (лежит на 6) -> -1
```

Разберём каждую строчку.

- **Пустой массив.** `n = 0`, значит, `high = n - 1 = -1`. Условие
  `low <= high` — это `0 <= -1`, ложь. Цикл не выполняется **ни разу**,
  функция сразу возвращает `-1`. Никакого обращения к `a[mid]` не
  происходит — именно поэтому важно, что `high` считается как `n - 1`, а
  проверка стоит **до** тела цикла.
- **Один элемент.** `low = high = 0`, условие `0 <= 0` истинно,
  `mid = 0 + (0 - 0) / 2 = 0`. Проверяем единственный элемент. Если это
  наше число — вернули `0`; если нет — двинули границу, зона схлопнулась,
  вернули `-1`. Тот самый случай, ради которого в условии стоит `<=`, а
  не `<`.
- **Первый и последний элементы** находятся нормально: `0` и `5`. Здесь
  часто ошибаются в границах — заводят `high = n` вместо `n - 1` и
  выходят за массив.
- **Число вне диапазона** (`0` меньше всех, `12` больше всех) даёт `-1`.
  Границы сходятся и перехлёстываются, лишних обращений к памяти нет.
- **Повторы.** Вот здесь надо остановиться. В массиве `2 4 4 4 4 7 9`
  четвёрка лежит на позициях 1, 2, 3 и 4. Функция вернула `3`. Не первую
  и не последнюю — **какую попалось**, ту, куда угодила середина.

Это не баг, а свойство алгоритма: бинарный поиск обещает найти **одно из
совпадений**, и не обещает, какое именно. Пока ты просто спрашиваешь
«есть или нет» — разницы никакой. Но если тебе нужна **первая** позиция
(или последняя, или сколько всего повторов) — обычный бинарный поиск не
подходит, его надо дорабатывать. Обещание функции стоит записать прямо в
комментарии над ней, чтобы через полгода не гадать.

- **Неотсортированный массив.** Последний блок — тот самый массив из
  начала главы, `17 4 42 8 15 23 16`. Все семь чисел в нём есть. Бинарный
  поиск нашёл только четыре: 17, 42 и 16 он объявил отсутствующими.
  Проследи за семнадцаткой: `low = 0`, `high = 6`, `mid = 3`, там `8`.
  Восьмёрка меньше семнадцати, значит (по логике алгоритма) искать надо
  правее — `low = 4`. А семнадцать лежит на позиции 0, слева. Всё,
  потеряли. И заметь: программа не упала, не заругалась, а спокойно
  ответила `-1`. Это самый опасный сорт ошибки — тихий.

Чтобы убедиться, что за границы массива мы нигде не залезли, соберём эту
же программу с двумя санитайзерами: `undefined` ловит запрещённую
арифметику, а `address` — обращения к чужой памяти:

```text
cc -std=c11 -Wall -Wextra -g -fsanitize=address,undefined \
   07-binary-edge.c -o 07-binary-edge-san
./07-binary-edge-san
```

Вывод получается ровно тот же, ни одной жалобы. Значит, чтения из чужой
памяти не было — в том числе на пустом массиве.

## Во сколько раз бинарный быстрее

Линейный поиск в худшем случае делает `n` сравнений. Бинарный на каждом
шаге (одном проходе цикла `while`) **делит** зону пополам. Сколько
шагов нужно в худшем случае? Столько, сколько раз зону можно поделить
пополам, пока в ней не останется один элемент, — и ещё один шаг, чтобы
проверить этот последний элемент.

«Сколько раз число делится пополам» — это **двоичный логарифм**. Пишут
его `log₂ n` (в коде и таблицах — `log2 n`). Определение такое:
`log₂ n` — это степень, в которую надо возвести 2, чтобы получить `n`.
Два в третьей степени — восемь (`2 · 2 · 2 = 8`), значит, `log₂ 8 = 3`:
восьмёрку можно поделить пополам ровно три раза (8 → 4 → 2 → 1). Два в
десятой — 1024, значит, `log₂ 1024 = 10`. Если `n` не степень двойки,
логарифм выходит дробным: `log₂ 1000 ≈ 9.97`. Нам дробная часть не
нужна — половинку элемента не проверишь, — поэтому округляем вниз.
Округление вниз записывают скобками `⌊ ⌋`: `⌊9.97⌋ = 9`. Итого для
нашей функции:

```text
шагов в худшем случае = ⌊log₂ n⌋ + 1
```

Проверим на массиве из шести, где мы искали руками: `log₂ 6 ≈ 2.58`,
вниз — 2, плюс один — 3. Ровно три шага мы и сделали, когда искали 7 и 8.

А теперь почувствуй разницу на больших числах:

```text
размер массива n   линейный (до n)   бинарный (⌊log₂ n⌋ + 1)
            10              10                 4
           100             100                 7
         1 000           1 000                10
     1 000 000       1 000 000                20
 1 000 000 000   1 000 000 000                30
```

Числа в правом столбце не на глаз: я перебрал программой все возможные
искомые (и те, что есть в массиве, и те, что попадают между ними) и
взял самый долгий поиск. Для 10, 100, 1000 и миллиона вышло ровно 4, 7,
10 и 20 шагов, а миллиард — просто по формуле.

В массиве из тысячи элементов линейный поиск может сделать до 1000
проверок, а бинарный — не больше 10 шагов. Это в сотню раз меньше
работы. А на миллиарде элементов разница уже в десятки миллионов раз: 30
шагов против миллиарда. Вот почему отсортированные данные так ценят: по
ним можно искать почти мгновенно.

Одна оговорка про слово «шаг». За один шаг наша функция сравнивает
`a[mid]` с `target` один раз (если попала) или два (`==`, потом `<`).
Так что сравнений у бинарного поиска до `2 · (⌊log₂ n⌋ + 1)` — для
тысячи элементов до 20. Против тысячи у линейного это всё равно ничто.

Удвой массив — линейному добавится столько же работы, сколько было.
Бинарному добавится всего **один** шаг: `log₂ (2n) = log₂ n + 1`. В этом
вся магия деления пополам.

### Проверим на секундомере

Таблица — это теория. Замерим настоящим временем: возьмём массив на
миллион отсортированных чисел и по 10 000 раз поищем в нём последний
элемент (худший случай для линейного поиска). Секундомер — `clock()` из
`<time.h>`; таким же замером в главе 5 мы сравнивали две проверки на
простоту, но саму функцию тогда не разбирали. Пора:

```c
int n = 1000000;
int *a = malloc((size_t)n * sizeof(int));
for (int i = 0; i < n; i++) {
    a[i] = i * 2;                    /* уже отсортирован */
}
int queries = 10000;
int last = (n - 1) * 2;
long long sink = 0;

clock_t t0 = clock();
for (int q = 0; q < queries; q++) {
    sink += linear_search(a, n, last);
}
double lin = (double)(clock() - t0) / CLOCKS_PER_SEC;

t0 = clock();
for (int q = 0; q < queries; q++) {
    sink += binary_search(a, n, last);
}
double bin = (double)(clock() - t0) / CLOCKS_PER_SEC;
```

Разбор новых мест:

- `clock()` возвращает, сколько процессорного времени истратила
  программа с начала работы, в условных единицах — «тиках» часов. Тип
  результата — `clock_t`. Само число ни о чём не говорит: сколько тиков
  в секунде, стандарт Си оставляет на усмотрение системы, и лежит это
  число в константе `CLOCKS_PER_SEC` (на macOS и Linux — миллион).
  Поэтому разницу делим на неё и получаем секунды.
- `(double)` перед разностью обязательно: обе величины целые, и без
  приведения деление ушло бы нацело (глава 2) — дробная часть
  пропала бы. Три с лишним секунды линейного поиска превратились бы в
  ровно 3, а тысячные доли секунды у бинарного — в 0.
- `sink` — «копилка»: складываем туда все найденные индексы. Зачем? Если
  результат поиска никуда не девать, компилятор с `-O2` вправе заметить,
  что вызов бесполезен, и выбросить весь цикл. Тогда мы замерим пустоту и
  получим восхитительный, но враньём добытый ноль. Копилка делает
  результат «нужным».

Полная программа лежит в `code/07-bench.c`. Она меряет ещё и третий
случай — бинарный поиск, который каждый раз ищет **другое** число. Вот
свежий запуск на моей машине:

```text
cc -std=c11 -Wall -Wextra -O2 07-bench.c -o 07-bench
./07-bench
массив: 1000000 элементов, по 10000 поисков
линейный, всегда последний:   3.3934 c  ( 339.34 мкс на поиск)
бинарный, всегда последний:   0.0002 c  (   0.02 мкс на поиск)
бинарный, каждый раз новый:   0.0012 c  (   0.12 мкс на поиск)
линейный медленнее бинарного примерно в 2807 раз
(контрольная сумма индексов: 24990385000)
```

Три с лишним секунды против одной тысячной. На один поиск: 339
микросекунд у линейного и 0.12 микросекунды у бинарного — разница почти
в три тысячи раз. (Три запуска подряд на одной машине дали 2441, 2766 и
2807 раз: секундомер немного плавает, порядок — нет.)

Сверим с теорией. Линейный поиск последнего элемента делает миллион
сравнений, бинарный — не больше 20 шагов. Отношение — 50 000, а
секундомер показал около 3000. Расхождение не ошибка: шаг бинарного
поиска дороже одного сравнения линейного (посчитать середину, прыгнуть
в другое место памяти), а линейный идёт по памяти подряд — это самый
удобный для процессора порядок. Теория говорит, **как растёт** работа,
а не сколько секунд займёт каждый шаг.

Почему две строки про бинарный? Когда мы 10 000 раз подряд ищем **одно и
то же** число, поиск каждый раз идёт по одному и тому же маршруту:
процессор держит нужные ячейки под рукой и заранее угадывает все
повороты. Выходит 0.02 микросекунды — красиво, но нечестно: так в жизни
не бывает. Когда число каждый раз новое, маршрут новый, данные приходится
тянуть из памяти — и получается 0.12 микросекунды. В несколько раз хуже
(точнее не скажешь: 0.0002 секунды — это уже на пределе точности
секундомера) и всё равно в тысячи раз быстрее линейного. Мерить надо на том, что похоже
на настоящую нагрузку, иначе замер льстит.

Абсолютные секунды у тебя будут свои — они зависят от машины. Но порядок
разницы воспроизведётся: тысячи раз.

Обрати внимание: сам массив мы отсортированным **сделали** — просто
заполнили по возрастанию. В реальной задаче за сортировку ещё нужно
заплатить, и об этой цене — следующая глава.

## Частые ошибки

**Бинарный поиск по неотсортированному массиву.** Ошибка номер один. Если
массив не отсортирован, «отбросить половину» бессмысленно: мы только что
видели, как на массиве `17 4 42 8 15 23 16` поиск не нашёл три числа из
семи, хотя они там лежали. Функция **молча** даёт неверный ответ, не
падает и не ругается. Прежде чем искать бинарно — убедись, что массив
отсортирован.

**Бесконечный цикл из-за неверного сдвига границ.** Если написать
`low = mid` вместо `low = mid + 1` (или `high = mid` вместо `high = mid - 1`),
зона может перестать уменьшаться, и `while` закрутится навсегда. Всегда
двигай границу **за** середину: `mid + 1` или `mid - 1`. Если программа
зависла — Ctrl+C, и проверь эти две строки.

**`<` вместо `<=` в условии цикла.** С `while (low < high)` ты пропустишь
случай, когда в зоне остался последний единственный элемент (`low == high`),
и не найдёшь число, стоящее именно там. Нужно `while (low <= high)`.

**Середина через `(low + high) / 2`.** На учебных массивах работает
безупречно — переполнение начинается только около миллиарда элементов. Но
привычка важнее: пиши `low + (high - low) / 2` всегда, чтобы однажды не
искать этот баг неделю.

**`high = n` вместо `high = n - 1`.** Последний индекс массива из `n`
элементов — это `n - 1`. Напишешь `n` — и на первом же шаге функция
прочитает `a[n]`, элемент за границей. Программа при этом может не упасть
и вернуть правдоподобную чушь; санитайзер `-fsanitize=address` такое
ловит сразу.

**Ждать от поиска первое совпадение.** Если чисел-дубликатов несколько,
бинарный поиск вернёт **какое-то** из них, а не самое левое (мы это
видели: в `2 4 4 4 4 7 9` для четвёрки вышел индекс 3). Нужна именно
первая позиция — алгоритм придётся дописать.

**Пустой массив забыли проверить.** Хорошая новость: наша версия
справляется сама. `high = n - 1 = -1`, условие `low <= high` сразу ложно,
цикл не запускается, возвращается `-1`. Но это работает только потому,
что проверка стоит **до** тела цикла. Переделаешь на `do { ... } while` —
получишь чтение из `a[0]` в пустом массиве.

**Перепутаны направления.** Если массив отсортирован по возрастанию и
`a[mid] < target`, цель **правее** — двигаем `low`. Перепутаешь `low` и
`high` местами — поиск будет уходить не туда и ничего не найдёт.

**Линейный поиск без выхода (`return` в цикле).** Если забыть `return i` и
просто печатать совпадения, цикл прогонит весь массив зря, а функция не
сможет вернуть индекс. Нашёл — возвращай сразу.

## Упражнения

1. Добавь в линейный поиск **счётчик сравнений**: пусть функция через
   указатель-параметр (вспомни `&` и `*` из главы 3) сообщает в `main`,
   сколько раз сравнила элементы. Поищи число, стоящее последним, и
   убедись, что счётчик равен длине массива. *Ответ:* на массиве из
   главы `17 4 42 8 15 23 16` поиск шестнадцати вернёт индекс 6, а
   счётчик покажет 7. Подсказка по сигнатуре:
   `int linear_search(const int a[], int n, int target, int *cmps)`,
   в начале `*cmps = 0;`, в цикле перед сравнением `(*cmps)++;`, в
   `main` — вызов с `&count`.

2. Сделай то же для бинарного поиска (считай шаги — проходы цикла
   `while`) и сравни счётчики на одном и том же отсортированном массиве
   из 15 элементов. Во сколько раз меньше шагов? *Ответ:* возьми
   `1 3 5 ... 29` и ищи последнее число, 29. Линейный сделает 15
   сравнений, бинарный — 4 шага (середины 7, 11, 13, 14), почти вчетверо
   меньше. Хуже 4 шагов бинарный на 15 элементах не бывает:
   `⌊log₂ 15⌋ + 1 = 3 + 1 = 4`.

3. Напиши `int count_occurrences(const int a[], int n, int target)` —
   функцию, которая считает, **сколько раз** число встречается в массиве
   (линейным проходом, без `return` на первом совпадении). *Ответ:* на
   `2 4 4 4 4 7 9` для четвёрки — 4, для пятёрки — 0.

4. Измени бинарный поиск так, чтобы он искал в массиве, отсортированном
   **по убыванию** (например, `11 9 7 5 3 1`). Что нужно поменять в двух
   ветках со сдвигом границ? *Ответ:* только знак в проверке: при
   `a[mid] > target` искомое лежит **правее** (`low = mid + 1`), иначе —
   левее (`high = mid - 1`). На `11 9 7 5 3 1` поиск 7 даст 2, поиск
   11 — 0, поиск 1 — 5, поиск 8 — `-1`.

5. Дай пользователю ввести искомое число с клавиатуры (`scanf`), а потом
   найди его бинарным поиском в захардкоженном отсортированном массиве.
   Не забудь проверить результат `scanf` (см. главу 6). *Ожидаемо:* на
   массиве `1 3 5 7 9 11` ввод `9` печатает позицию 4, ввод `4` —
   «не найдено», ввод `abc` — сообщение об ошибке ввода, а не поиск по
   мусору.

6. Подумай и проверь на бумаге: сколько шагов сделает бинарный поиск на
   массиве из 16 элементов в худшем случае? А из 17? Совпало ли с твоей
   догадкой про `log2`? *Ответ:* 5 и 5. `log₂ 16 = 4` ровно, плюс
   последний шаг — 5. У 17 логарифм `≈ 4.09`, вниз — снова 4, плюс
   один — 5. Шестой шаг понадобится только с 32 элементов.

7. **Первое совпадение.** Доработай бинарный поиск так, чтобы на массиве
   `2 4 4 4 4 7 9` он для четвёрки возвращал `1`, а не `3`. Подсказка:
   нашёл совпадение — не возвращайся сразу, а запомни индекс в отдельную
   переменную и продолжай искать **левее** (`high = mid - 1`). Когда зона
   схлопнется, в переменной останется самый левый найденный индекс.
   *Ответ:* для 4 — `1`, для 2 — `0`, для 5 — `-1`. Шагов по-прежнему не
   больше `⌊log₂ n⌋ + 1`: мы не перебираем повторы, а продолжаем делить
   зону пополам.

8. **Сломай нарочно.** Возьми `07-binary.c`, замени `high = n - 1` на
   `high = n`, а искомое число сделай **больше всех** в массиве
   (например, 12). Собери с `-fsanitize=address` и запусти. Санитайзер
   напечатает `stack-buffer-overflow` и покажет строку с `a[mid]` — это
   чтение элемента `a[6]`, которого нет. Потом верни как было. Заметь,
   что без санитайзера программа спокойно отвечает «не найдено» и не
   подаёт виду. (Собери именно без `-O2`: с оптимизацией компилятор
   может переложить массив из стека в другое место памяти, и отчёт будет
   называться `global-buffer-overflow`, — ошибка та же.)

## Что мы получили

Теперь у тебя два инструмента поиска. **Линейный** — простой и
всеядный: работает на любом массиве, но в худшем случае проверяет все `n`
элементов. **Бинарный** — стремительный (не больше `⌊log₂ n⌋ + 1`
шагов вместо `n`), но
требует **отсортированного** массива и аккуратной работы с границами
`low`/`high`/`mid`. Ты увидел, как функция возвращает индекс или `-1`,
почему середину считают через `low + (high - low) / 2`, и насколько
бешеной становится разница в скорости на больших данных.

Заодно ты приобрёл две привычки, которые пригодятся до конца книги.
Первая — **гонять алгоритм по краям**: пустой вход, один элемент, самое
начало, самый конец, повторы, «нет такого». Красивый пример работает у
всех, ломается всё на краях. Вторая — **не верить замерам и заявлениям на
слово**: собрать, запустить, посмотреть на настоящие секунды, включить
санитайзер и дать программе самой рассказать, где она врёт.

И тут всплывает честный вопрос: бинарный поиск великолепен, но он держится
на одном условии — массив должен быть **отсортирован**. А что, если данные
пришли вперемешку? Значит, перед поиском их надо упорядочить. Как
расставить элементы по возрастанию — большая и интересная тема. Ею мы и
займёмся в следующей главе: разберём **сортировки**, после чего бинарный
поиск станет применим к любым данным, а не только к заранее аккуратным
спискам.
