# Приложение А. Задачи с собеседований: Junior

Книга закончилась, а собеседования только начинаются. Это приложение —
сборник задач, которые реально дают на собеседовании C-разработчику
уровня **Junior** (младший, начинающий). Здесь нет ничего, чего ты не
проходил: всё опирается на главы 1–18 — числа, массивы, строки,
указатели, циклы, функции. Новой теории не будет. Будет другое — взгляд
на знакомые приёмы глазами интервьюера.

На собесе мало написать работающий код. Спрашивающий смотрит, **как ты
думаешь**: учёл ли краевые случаи, помнишь ли про переполнение,
понимаешь ли, что делает каждая строка. Поэтому к каждой задаче я
добавил блок «что спросят дальше» — те самые уточняющие вопросы,
которыми тебя будут «дожимать».

## Как пользоваться

Каждая задача оформлена так:

- **Условие** — как её формулируют вслух на собесе.
- **Идея** — как к ней подступиться, без кода.
- **Решение** — рабочий код.
- **Разбор** — почему так, а не иначе, какая сложность, где края.
- **Что спросят дальше** — продолжения и подвохи.

Главный совет: **сначала реши сам**, на бумаге или в редакторе, и только
потом смотри решение. Подсмотренное решение забывается к утру.
Решённое самому — остаётся. Даже если решил криво — сравни с моим
вариантом, и разница тебе многое объяснит.

Приложение делится на три части:

1. **Задачи 1–8** — у каждой есть готовый файл `code/19-0N-*.c`, номер
   задачи совпадает с номером файла. Собирается и запускается так:

   ```text
   cc -std=c11 -Wall -Wextra -O2 code/19-07-prime.c -o prime
   ./prime
   ```

2. **Задачи 9–11** — три классики, которые решаются в несколько строк;
   отдельных файлов под них нет, весь код прямо в тексте.
3. **Каверзы** — короткие фрагменты «что выведет / в чём ошибка».
   Многие из них намеренно содержат ошибку или неопределённое
   поведение, поэтому в `code/` они не вынесены: в файлах книги лежит
   только код, который **можно** запускать.

Все выводы программ в этом приложении получены реальным запуском на
Apple clang 21 (x86-64, macOS). Где результат зависит от платформы или
от компилятора, я это отдельно оговариваю.

## Часть 1. Задачи с готовыми решениями

### Задача 1. Поменять местами две переменные

**Условие.** Есть две переменные `a` и `b`. Поменяй их значения
местами. После обмена в `a` должно лежать то, что было в `b`, и наоборот.

**Идея.** Наивная попытка «в лоб» не работает:

```c
a = b;   /* старое значение a потеряно навсегда */
b = a;   /* сюда попадёт b, а не старое a */
```

Первая же строка затирает `a`. Нужна **временная переменная**, чтобы
запомнить значение перед затиранием.

**Решение** (`code/19-01-swap.c`):

```c
#include <stdio.h>

int main(void)
{
    int a = 5;
    int b = 9;

    printf("До:    a = %d, b = %d\n", a, b);

    int temp = a;   /* запомнили a */
    a = b;          /* в a положили b */
    b = temp;       /* в b положили старое a */

    printf("После: a = %d, b = %d\n", a, b);
    return 0;
}
```

Запуск:

```text
До:    a = 5, b = 9
После: a = 9, b = 5
```

**Разбор.** `temp` хранит копию `a`, пока мы перезаписываем `a`
значением `b`. Потом достаём из `temp` старое `a` и кладём в `b`. Три
присваивания, ни одного условия, ни одного цикла — O(1) по времени и
O(1) по памяти (одна лишняя переменная). Работает для любых значений,
включая `INT_MIN` и `INT_MAX`: мы ничего не складываем и не вычитаем,
переполниться нечему.

**Что спросят дальше.** «А можно без временной переменной?» Да, два
способа.

Через арифметику:

```c
a = a + b;
b = a - b;   /* = старое a */
a = a - b;   /* = старое b */
```

Через XOR (исключающее «или», оператор `^`):

```c
a = a ^ b;
b = a ^ b;
a = a ^ b;
```

Проверим XOR на наших числах. 5 в двоичном виде — `0101`, 9 — `1001`.
`^` ставит 1 там, где биты **разные**:

```text
a = a ^ b:  0101 ^ 1001 = 1100   (a = 12, «смесь» a и b)
b = a ^ b:  1100 ^ 1001 = 0101   (b = 5  — старое a)
a = a ^ b:  1100 ^ 0101 = 1001   (a = 9  — старое b)
```

Работает, потому что `x ^ y ^ y == x`: повторный XOR с тем же числом
«снимает» его обратно. Арифметика устроена так же: в `a` лежит сумма
14, `14 - 9 = 5`, `14 - 5 = 9`. Оба фрагмента я собрал и запустил:
`a = 9, b = 5`.

Оба выглядят эффектно, и интервьюер любит про них спросить. Но честный
ответ — **в реальном коде так делать не надо**. Почему:

- Арифметический способ **переполняется**: если `a + b` вылезет за
  пределы `int`, это не «завернётся в минус», а неопределённое
  поведение — переполнение знакового типа стандарт не описывает вообще
  (см. главу 4 про переполнение; подробный разбор со всеми источниками
  UB — в Приложении В, каверза 1). Пример: `a = INT_MAX`, `b = 1` —
  санитайзер `-fsanitize=undefined` (см. главу «Как готовиться к
  собеседованию») ловит здесь три переполнения подряд. С `unsigned`
  этот трюк как раз корректен: беззнаковая арифметика по стандарту
  идёт по модулю 2^N и не переполняется.
- Оба трюка ломаются, если `a` и `b` — **одна и та же переменная**
  (один адрес). Так бывает в функции обмена через указатели:
  `swap(&x, &x)`, например когда сортировка меняет элемент сам с
  собой. XOR: `*a ^= *b` превращает `x` в `x ^ x`, то есть в 0, и
  дальше из нуля старое значение уже не достать. Сложение: `*a = x + x`,
  потом `*b = 2x - 2x` = 0 — тоже ноль. Я проверил на `x = 42`: оба
  варианта дают 0, а обмен через `temp` оставляет 42. Одинаковые
  **значения** в разных переменных (`a = 42`, `b = 42`) при этом
  не страшны — ломает именно общий адрес.
- XOR работает только с целыми: для `double` строка `a = a ^ b` просто
  не соберётся (`invalid operands to binary expression`).
- Оба варианта **нечитаемы** и не быстрее: современный компилятор и так
  оптимально реализует обмен через `temp` — на уровне ассемблера это
  часто просто две пересылки через регистры, а иногда компилятор
  вообще обходится без обмена, запомнив, в каком регистре что лежит.

Правильный вывод, который хочет услышать грамотный интервьюер: «знаю про
XOR-трюк, но в продакшене пишу через `temp` — понятнее и без подвохов».

Второе продолжение: «сделай так, чтобы обмен работал из функции». Это
уже задача про указатели, она разобрана в Приложении Б (задача 9).

### Задача 2. Развернуть строку на месте

**Условие.** Дана строка. Переверни её **на месте** — без создания
второго массива.

**Идея.** Два индекса: один на начало (`left`), другой на конец
(`right`). Меняем символы местами и идём навстречу, пока они не
встретятся посередине.

Проверим руками на слове `abcde` (пять символов, индексы 0…4):

```text
шаг 0:  a b c d e     left=0, right=4  →  меняем a и e
шаг 1:  e b c d a     left=1, right=3  →  меняем b и d
шаг 2:  e d c b a     left=2, right=2  →  left < right ложно, стоп
```

Средний символ `c` остался на месте — так и должно быть.

**Решение** (`code/19-02-reverse-string.c`):

```c
#include <stdio.h>
#include <string.h>

/* Переворачивает строку на месте, без второго массива. */
void reverse(char *s)
{
    int left = 0;
    int right = (int)strlen(s) - 1;
    while (left < right) {
        char tmp = s[left];
        s[left] = s[right];
        s[right] = tmp;
        left++;
        right--;
    }
}

int main(void)
{
    char text[] = "Hello, world";
    reverse(text);
    printf("%s\n", text);
    return 0;
}
```

Запуск:

```text
dlrow ,olleH
```

**Разбор.** `strlen(s)` — длина строки без учёта завершающего нуля
`'\0'` (см. главу 10). Возвращает она `size_t` — беззнаковый тип; мы
приводим результат к `int`, потому что `right` должен уметь стать
отрицательным. Если бы `right` был `size_t`, то для **пустой** строки
`strlen(s) - 1` дало бы не −1, а огромное число (беззнаковое
вычитание заворачивается), и цикл полез бы за границы массива. Это
типичная ловушка со знаковостью, о ней стоит сказать вслух.

Внутри цикла — обычный обмен через `tmp` (как в задаче 1). Условие
`left < right` останавливает нас на середине: средний символ при
нечётной длине трогать не нужно.

**Сложность.** O(n) по времени: `strlen` один раз проходит строку
целиком, а потом делаем ⌊n/2⌋ обменов (n/2 с округлением вниз: для
`abcde` при n = 5 — два обмена). O(1) по дополнительной памяти — новый буфер не
выделяли.

**Краевые случаи.** Пустая строка `""`: `strlen` даёт 0, `right` = −1,
условие `0 < -1` ложно, цикл не выполняется — правильно. Строка из
одного символа: `left = right = 0`, тоже ноль итераций. Строка из двух:
ровно один обмен.

**Что спросят дальше.**

- «Почему `char text[] = "..."`, а не `char *text = "..."`?» Менять
  строковый литерал стандарт запрещает — это неопределённое поведение,
  а на практике литералы обычно лежат в памяти только для чтения, и
  программа падает. Массив `char text[]` —
  твоя изменяемая копия литерала, её менять можно. Подробный разбор с
  двумя разными сборками одной программы — в Приложении Б, каверза 1.
- «А если в строке кириллица?» Развернётся мусор: в UTF-8 русская буква
  занимает два байта, и посимвольный разворот перемешает половинки букв.
  Наш `reverse` разворачивает **байты**, а не буквы. Для UTF-8 нужен
  разбор по символам — это честный и правильный ответ.
- «Сделай без `strlen`.» Найди конец сам: `int right = 0;`, потом
  `while (s[right] != '\0') right++;` и `right--`. Ровно то же самое,
  что делает `strlen`.

### Задача 3. Проверка палиндрома

**Условие.** Палиндром читается одинаково слева направо и справа налево
(`level`, `radar`). Проверь, палиндром ли данная строка.

**Идея.** Та же пара индексов с краёв, но теперь не меняем символы, а
**сравниваем**. Нашли несовпадение — сразу не палиндром, дальше можно не
смотреть.

**Решение** (`code/19-03-palindrome.c`):

```c
#include <stdio.h>
#include <string.h>

/* Возвращает 1, если строка — палиндром, иначе 0. */
int is_palindrome(const char *s)
{
    int left = 0;
    int right = (int)strlen(s) - 1;
    while (left < right) {
        if (s[left] != s[right]) {
            return 0;   /* нашли несовпадение — это не палиндром */
        }
        left++;
        right--;
    }
    return 1;
}

int main(void)
{
    const char *words[] = {"level", "radar", "hello", "noon"};
    for (int i = 0; i < 4; i++) {
        if (is_palindrome(words[i])) {
            printf("%s — палиндром\n", words[i]);
        } else {
            printf("%s — нет\n", words[i]);
        }
    }
    return 0;
}
```

Запуск:

```text
level — палиндром
radar — палиндром
hello — нет
noon — палиндром
```

**Разбор.** Параметр `const char *s` — обещание «эту строку я менять не
буду, только читаю». `words` — массив указателей на строковые литералы,
и объявлен он как `const char *words[]`: менять литералы нельзя, и мы
честно фиксируем это в типе.

Отсюда следствие, которое любят проверять. Убери `const` у параметра — и
вызов `is_palindrome(words[i])` перестанет собираться молча:

```text
pal.c:23:27: warning: passing 'const char *' to parameter of type
'char *' discards qualifiers
[-Wincompatible-pointer-types-discards-qualifiers]
   23 |         if (is_palindrome(words[i])) {
      |                           ^~~~~~~~
pal.c:5:25: note: passing argument to parameter 's' here
    5 | int is_palindrome(char *s)
      |                         ^
1 warning generated.
```

(Длинную первую строку я перенёс, чтобы она влезла в страницу; имя
файла у тебя будет своё.)

Правило одностороннее: `char *` передать туда, где ждут `const char *`,
можно, а обратно — нет. Поэтому `const` на входном параметре тебя не
ограничивает, а наоборот — расширяет круг того, что функции можно
скормить.

`return 0` при первом же несовпадении — это **ранний выход**: нет смысла
проверять дальше, ответ уже ясен.

**Сложность.** Худший случай (строка действительно палиндром) — ⌊n/2⌋
сравнений, то есть O(n). Лучший случай — одно сравнение, если первый и
последний символы разные. Плюс один проход `strlen` в начале — он тоже
O(n). Памяти O(1).

**Краевые случаи.** Пустая строка и строка из одного символа считаются
палиндромами — цикл не выполняется, возвращается 1. Это общепринятая
трактовка, но на собесе её лучше проговорить вслух: «пустую строку
считаю палиндромом, если надо иначе — скажи».

**Что спросят дальше.**

- «Сделай регистронезависимо: `Level` тоже палиндром.» Сравнивай не
  `s[left]` и `s[right]`, а их версии в одном регистре (приём приведения
  к нижнему регистру — в задаче 6 про гласные).
- «А если игнорировать пробелы и знаки: `A man a plan a canal Panama`?»
  Тогда индексы нужно «перепрыгивать» через не-буквы:

  ```c
  while (left < right && !isalpha((unsigned char)s[left]))  left++;
  while (left < right && !isalpha((unsigned char)s[right])) right--;
  ```

  Эти две строки ставятся в начало тела цикла, перед сравнением;
  `isalpha` («это буква?») живёт в `<ctype.h>`. Приведение к
  `unsigned char` тут обязательно — почему, разбираем в каверзе 4.
- «Проверь палиндром рекурсивно.» Функция сравнивает края и вызывает
  себя для внутренней части. Работает, но глубина рекурсии — около n/2
  вызовов, то есть O(n) памяти стека (см. главу 9), — итеративно
  лучше.

### Задача 4. Факториал итеративно

**Условие.** Посчитай факториал числа `n` циклом (без рекурсии).
`n! = 1·2·…·n`, при этом `0! = 1`.

**Идея.** Накопитель `fact = 1`, домножаем на 2, 3, …, n. Стартовое
значение — **единица**, а не ноль (умножение на 0 всё обнулит). И сразу
помним про переполнение из главы 4.

**Решение** (`code/19-04-factorial.c`):

```c
#include <stdio.h>

int main(void)
{
    int n;
    printf("Факториал какого числа? ");
    if (scanf("%d", &n) != 1) {
        printf("Это не число.\n");
        return 1;
    }

    if (n < 0) {
        printf("Факториал определён только для n >= 0.\n");
        return 1;
    }
    if (n > 20) {
        printf("Слишком большое: long long переполнится при n > 20.\n");
        return 1;
    }

    long long fact = 1;   /* 0! = 1 и 1! = 1 — стартуем с единицы */
    for (int i = 2; i <= n; i++) {
        fact = fact * i;
    }

    printf("%d! = %lld\n", n, fact);
    return 0;
}
```

Запуск:

```text
Факториал какого числа? 13
13! = 6227020800
```

**Разбор.** Тип накопителя — `long long` (на этой машине 8 байт),
потому что `int` лопается уже на 13!: 6 227 020 800 больше, чем
`INT_MAX` = 2 147 483 647. Печатаем через `%lld` — свой спецификатор для
`long long`; напишешь `%d`, и `printf` возьмёт из аргументов не то
количество байт, получится мусор (а компилятор с `-Wall` заругается).

Цикл идёт с 2, потому что умножать на 1 бессмысленно. Для `n = 0` и
`n = 1` он не выполнится ни разу, и `fact` останется 1 — верный ответ
без всякого отдельного `if`.

`scanf("%d", &n)` возвращает **количество успешно прочитанных
значений**. Мы сравниваем его с 1: если пользователь ввёл `abc`, `scanf`
вернёт 0, и мы честно скажем «это не число», а не станем считать
факториал мусора. Пропущенная проверка `scanf` — одна из самых частых
претензий на собеседовании.

**Сложность.** O(n) умножений, O(1) памяти. Для `n ≤ 20` это не больше
девятнадцати умножений (от 2 до 20).

**Что спросят дальше.**

- «До какого `n` это корректно?» До 20: 20! = 2 432 902 008 176 640 000
  ещё помещается в `long long` (предел 9 223 372 036 854 775 807), а
  21! — уже нет. Поэтому мы заранее отсекаем `n > 20`. Грамотный
  кандидат **сам** проговаривает границу типа, не дожидаясь вопроса.
- «А если бы отсечки не было?» Получили бы переполнение знакового типа —
  это UB, а не «просто неверное число». Программа имеет право напечатать
  что угодно.
- «А если ввести 2147483648?» Проверь сам: программа ответит
  «Факториал определён только для n >= 0.». Число не влезло в `int`, а
  для `scanf` с `%d` такой ввод — неопределённое поведение (стандарт
  C11, раздел 7.21.6.2); на этой машине в `n` оказалось отрицательное
  число. Проверка «`scanf` вернул 1» от этого не спасает. Надёжный
  способ — читать строку и разбирать её самому с контролем
  переполнения, как в Приложении В, задача 4.
- «А рекурсией?» Можно (см. главу 9), но итеративно — без риска
  переполнить стек вызовов на больших `n` и обычно быстрее.
- «А факториал 100?» В `long long` не влезет никогда. Нужна «длинная
  арифметика»: хранить число как массив цифр и умножать столбиком.

### Задача 5. Второй по величине элемент массива

**Условие.** Найди второй по величине элемент массива за **один** проход
(не сортируя).

**Идея.** Держим две переменные: `max` (наибольший) и `second`
(второй). Для каждого числа: если оно больше `max` — старый `max`
становится `second`, а само число новым `max`. Иначе, если оно меньше
`max`, но больше `second` — обновляем `second`. Дубликаты максимума
вторым считать не должны.

**Решение** (`code/19-05-secondmax.c`):

```c
#include <stdio.h>
#include <limits.h>

int main(void)
{
    int a[] = {3, 9, 9, 1, 7, 9, 4};
    int n = (int)(sizeof(a) / sizeof(a[0]));

    int max = INT_MIN;     /* самое большое */
    int second = INT_MIN;  /* второе по величине */

    for (int i = 0; i < n; i++) {
        if (a[i] > max) {
            second = max;  /* бывший максимум становится вторым */
            max = a[i];
        } else if (a[i] > second && a[i] < max) {
            second = a[i]; /* не максимум, но больше второго */
        }
    }

    if (second == INT_MIN) {
        printf("Второго по величине нет.\n");
    } else {
        printf("Максимум: %d, второй: %d\n", max, second);
    }
    return 0;
}
```

Запуск:

```text
Максимум: 9, второй: 7
```

**Разбор.** `INT_MIN` из `<limits.h>` — самое маленькое значение `int`
(на этой машине −2147483648). Стартуем с него, чтобы любой реальный
элемент оказался больше.

Пройдём массив `{3, 9, 9, 1, 7, 9, 4}` руками:

```text
элемент  max      second   что произошло
   3     3        INT_MIN  первый больше max
   9     9        3        новый максимум, старый ушёл во второй
   9     9        3        не больше max и не меньше max — мимо обеих веток
   1     9        3        меньше second — мимо
   7     9        7        меньше max, больше second — обновили
   9     9        7        снова дубликат максимума — мимо
   4     9        7        меньше second — мимо
```

Максимум 9 встречается трижды, но вторым выводится 7, а не 9 — условие
`a[i] < max` отсекает дубликаты максимума. Это именно тот случай,
который любят подсунуть.

**Сложность.** Один проход — O(n) сравнений, O(1) памяти. Через
сортировку было бы O(n log n), и интервьюер обязательно спросит, почему
ты не отсортировал: потому что нам нужен один элемент, а не порядок.

**Что спросят дальше.**

- «Что если в массиве все элементы одинаковы (`{5,5,5}`)?» Тогда второго
  по величине нет — наш код напечатает «Второго по величине нет.»,
  потому что
  `second` так и остался `INT_MIN`. Уточни у интервьюера, считать ли
  дубликат вторым: трактовки бывают разные, и важно проговорить выбор.
- «А если в массиве честно лежит `INT_MIN`?» Тогда наш признак «второго
  нет» ложно сработает на массиве `{5, INT_MIN}`: второй там есть, это
  `INT_MIN`, а программа скажет «нет». Лечится флагом
  `int have_second = 0;` вместо сравнения с `INT_MIN`. Хороший ответ,
  который показывает, что ты видишь дырку в собственном решении.
- «А массив из одного элемента?» Максимум найдётся, второго не будет —
  код напечатает «Второго по величине нет.», и это верно.
- «А пустой массив?» Тоже «Второго нет», но и `max` останется
  `INT_MIN`, хотя максимума у пустого массива нет вообще. В функции,
  которая возвращает результат, на `n < 2` сразу возвращают признак
  ошибки.
- «А k-й по величине?» Обобщение — там уже нужна частичная сортировка,
  куча (heap) или алгоритм быстрого выбора (quickselect). Это уже
  уровень Middle и выше.

### Задача 6. Подсчёт гласных в строке

**Условие.** Посчитай, сколько гласных букв в строке (английские
a, e, i, o, u в любом регистре).

**Идея.** Идём по строке посимвольно до `'\0'`. Для каждого символа
проверяем, не гласная ли он. Чтобы не плодить проверки для верхнего и
нижнего регистра, приводим символ к нижнему.

**Решение** (`code/19-06-vowels.c`):

```c
#include <stdio.h>
#include <string.h>

/* Возвращает 1, если c — английская гласная (любого регистра). */
int is_vowel(char c)
{
    char lower = c;
    if (c >= 'A' && c <= 'Z') {
        lower = (char)(c - 'A' + 'a');   /* привели к нижнему регистру */
    }
    return lower == 'a' || lower == 'e' || lower == 'i'
        || lower == 'o' || lower == 'u';
}

int main(void)
{
    const char *s = "Programming In C";
    int count = 0;
    for (int i = 0; s[i] != '\0'; i++) {
        if (is_vowel(s[i])) {
            count++;
        }
    }
    printf("В строке \"%s\" гласных: %d\n", s, count);
    return 0;
}
```

Запуск:

```text
В строке "Programming In C" гласных: 4
```

Считаем руками: `o`, `a`, `i` в `Programming` и `I` в `In` — четыре.
Буква `C` не гласная, пробелы тоже.

**Разбор.** Трюк `c - 'A' + 'a'` переводит заглавную букву в строчную.
Символы в C — это коды (см. главу 2): буквы `A..Z` идут в ASCII подряд,
и `a..z` тоже подряд. Разница между заглавной и строчной одной буквы
постоянна и равна `'a' - 'A'` = 97 − 65 = 32, поэтому сдвиг работает
для всех букв разом. (Строго говоря, стандарт Си не обещает ASCII и
не обещает, что буквы идут подряд, — это обещают только для цифр
`'0'..'9'`. Но на всех машинах, где ты будешь это запускать, кодировка
совместима с ASCII.) Приведение `(char)` — явная пометка «сужаю
обратно в `char`, так задумано»: арифметика в Си поднимает `char` до
`int`, и результат выражения — `int`. clang 21 здесь молчит даже с
`-Wconversion`, но другие компиляторы на такое неявное сужение могут
предупредить.

Условие цикла `s[i] != '\0'` — канонический способ пройти строку до
завершающего нуля. Как только упёрлись в него, строка кончилась.

**Сложность.** O(n) — один проход, по одному сравнению на символ.
Памяти O(1).

**Что спросят дальше.**

- «А `<ctype.h>`?» В стандартной библиотеке есть `tolower()` — он делает
  ровно наш сдвиг и уважает локаль. Но у него важная тонкость: аргумент
  надо приводить к `unsigned char`, иначе байт с кодом больше 127 в
  знаковом `char` превратится в отрицательное число, и получишь UB. Правильно так:
  `char lower = (char)tolower((unsigned char)c);`. Почему — разбираем в
  каверзе 4. На собесе ценят, когда ты знаешь про готовое, но умеешь и
  руками, и помнишь про эту ловушку.
- «Учитывай 'y'.» Расширение списка — проверка внимательности: в
  английском `y` считается гласной не всегда, и стоит уточнить условие.
- «А русские гласные?» Не через `char`: в UTF-8 русская буква — два
  байта, посимвольная проверка сломается. Нужен разбор UTF-8 или
  широкие символы `wchar_t`.

### Задача 7. Проверка на простое число

**Условие.** Дано число `n`. Определи, простое ли оно (делится только на
1 и на себя; 0, 1 и отрицательные — не простые).

**Идея.** Перебираем возможные делители от 2. Нашли хоть один — число
составное. Ключевая оптимизация: проверять делители только **до корня**
из `n`, потому что делители идут парами (`n = d · (n/d)`), и меньший из
пары всегда не больше √n: если бы оба множителя были больше √n, их
произведение было бы больше n. Для 36 пары такие: 2·18, 3·12, 4·9,
6·6 — и дальше они просто повторяются зеркально (9·4, 12·3, 18·2).
Значит, если до √n делителя нет, то его нет и после.

**Решение** (`code/19-07-prime.c`):

```c
#include <stdio.h>

/* Возвращает 1, если n — простое число, иначе 0. */
int is_prime(int n)
{
    if (n < 2) {
        return 0;             /* 0, 1 и отрицательные — не простые */
    }
    for (int d = 2; d <= n / d; d++) {   /* то же, что d * d <= n */
        if (n % d == 0) {
            return 0;         /* нашли делитель — составное */
        }
    }
    return 1;
}

int main(void)
{
    int n;
    printf("Введи число: ");
    if (scanf("%d", &n) != 1) {
        printf("Это не число.\n");
        return 1;
    }

    if (is_prime(n)) {
        printf("%d — простое\n", n);
    } else {
        printf("%d — не простое\n", n);
    }
    return 0;
}
```

Запуск:

```text
Введи число: 17
17 — простое
```

**Разбор.** Условие цикла `d <= n / d` — это и есть «до корня»: оно
верно ровно тогда, когда `d * d <= n`, то есть когда d не больше √n.
Проверим на 36: при `d = 6` имеем `36 / 6 = 6`, и `6 <= 6` — ещё
проверяем; при `d = 7` уже `36 / 7 = 5` (деление нацело), `7 <= 5`
ложно — стоп, и `7 * 7 = 49` тоже больше 36. Для простого 999 983
цикл проверит делители от 2 до 999 — это 998 делений вместо почти
миллиона при переборе до `n`.

Почему не написать проще, `d * d <= n`? Так пишут почти все, и это
ловушка: при `n` рядом с `INT_MAX` квадрат `d * d` сам вылезает за
пределы `int`. Разбор этой ловушки — ниже, в «что спросят дальше».

Случаи `n < 2` отсекаем сразу — иначе единица ошибочно сошла бы за
простую: цикл `d <= 1 / 2` при `d = 2` не выполнится ни разу, и функция
вернула бы 1.

**Сложность.** O(√n) делений в худшем случае (когда `n` простое и цикл
доходит до конца). Для составных чисел обычно гораздо быстрее: у
половины чисел делитель 2 находится на первой же итерации.

**Что спросят дальше.**

- «Почему не `d <= sqrt(n)`?» Чтобы не звать дробную функцию `sqrt`:
  не нужен `<math.h>` (а на Linux часто ещё и ключ `-lm` при сборке),
  нет перевода в `double` и обратно. Для `int` корень на обычной машине
  посчитается точно, но для `long long` больше 2^53 (около 9·10^15)
  `double` уже не хранит все целые подряд, и граница цикла может
  сдвинуться на единицу. Целочисленное сравнение точное всегда.
- «А почему не `d * d <= n`?» Потому что `d * d` может переполниться.
  46340² = 2 147 395 600 ещё помещается в `int`, а 46341² =
  2 147 488 281 уже больше `INT_MAX` = 2 147 483 647. Для составных
  чисел цикл обрывается раньше, но если `n` простое и больше
  2 147 395 600, цикл дойдёт до `d = 46341`, и умножение даст
  переполнение — UB. Такое число есть, и очень знакомое: сам `INT_MAX`,
  2 147 483 647, — простое. Я проверил: версия с `d * d <= n`, собранная
  с `-O2`, на нём отвечает «не простое» — неправда. `d <= n / d` не
  умножает вообще и переполниться не может. Назвать эту ловушку самому
  — сильный ход.
- «Ускорь ещё.» Проверять 2 отдельно, а дальше только нечётные делители
  (`d = 3; d += 2`) — вдвое меньше итераций.
- «Все простые до N?» Это уже **решето Эратосфена** (см. главу 5) —
  частый следующий шаг: O(N log log N) вместо N отдельных проверок,
  каждая до O(√N), то есть до O(N√N) в сумме.

### Задача 8. Цифры числа: сколько их и какая сумма

**Условие.** Дано целое число. Посчитай, сколько в нём цифр (123 → 3) и
чему равна их сумма (456 → 4+5+6 = 15).

**Идея.** Обе задачи решаются одним циклом. Делим число на 10 нацело,
пока оно не станет нулём: каждое деление откусывает одну цифру справа
(см. главу 4). Заодно на каждом шаге берём остаток `n % 10` — это и есть
откушенная цифра.

Разберём 456 руками:

```text
n = 456   digit = 456 % 10 = 6   sum = 6    count = 1   n = 45
n = 45    digit = 45  % 10 = 5   sum = 11   count = 2   n = 4
n = 4     digit = 4   % 10 = 4   sum = 15   count = 3   n = 0
n = 0  →  цикл кончился
```

**Решение** (`code/19-08-digits.c`):

```c
#include <stdio.h>

int main(void)
{
    int n;
    printf("Введи целое число: ");
    if (scanf("%d", &n) != 1) {
        printf("Это не число.\n");
        return 1;
    }

    long long m = n;   /* в long long модуль INT_MIN помещается */
    if (m < 0) {
        m = -m;        /* знак на количество и сумму цифр не влияет */
    }

    int count = 0;     /* сколько цифр */
    int sum = 0;       /* сумма цифр */

    if (m == 0) {
        count = 1;     /* у нуля одна цифра */
    }
    while (m > 0) {
        int digit = (int)(m % 10);
        sum += digit;
        count++;
        m /= 10;
    }

    printf("Цифр: %d, сумма цифр: %d\n", count, sum);
    return 0;
}
```

Запуск:

```text
Введи целое число: 90834
Цифр: 5, сумма цифр: 24
```

Проверяем: 9+0+8+3+4 = 24, цифр действительно пять.

**Разбор.** Считаем мы не в самом `n`, а в его копии `m` типа
`long long` — зачем, объясню в «что спросят дальше», это главный
подвох задачи. `m % 10` — последняя цифра, `m /= 10` (то же, что
`m = m / 10`) — отбрасываем её. `digit` вычисляем **один раз** и
кладём в переменную, чтобы не писать `m % 10` второй раз (см. главу 4,
шаг 3). `(int)` перед `m % 10` честно говорит: остаток от 0 до 9, в
`int` он помещается. `count` и `sum` стартуют с 0: накопитель суммы
всегда начинается с нейтрального элемента, для сложения это ноль.

Отдельный случай — само число **0**: цикл `while (m > 0)` для него не
выполнится ни разу, и `count` остался бы нулём, а ответ должен быть 1
(одна цифра). Поэтому ноль обрабатываем вручную. С суммой всё в порядке
и без этого: сумма цифр нуля равна нулю.

**Сложность.** Число итераций равно количеству цифр. Для n ≥ 1 цифр
ровно ⌊log₁₀ n⌋ + 1 (логарифм по основанию 10, округлённый вниз, плюс
один): у 90834 логарифм примерно 4,96, вниз — 4, плюс один — 5 цифр.
Отсюда сложность O(log n). Для `int` это максимум 10 шагов: у
2 147 483 647 десять цифр.

**Что спросят дальше.**

- «А отрицательные?» У −123 три цифры, минус не считается, поэтому мы
  берём модуль. И вот подвох: напиши просто `if (n < 0) n = -n;` в
  `int` — и для `INT_MIN` получишь UB, потому что у самого маленького
  `int` нет положительной пары (диапазон несимметричен: от
  −2 147 483 648 до 2 147 483 647, и 2 147 483 648 в `int` не
  влезает). Я проверил такую версию: с `-O2` она на −2147483648 случайно
  печатает верное `Цифр: 10, сумма цифр: 47`, а собранная с
  `-fsanitize=undefined` — ругается на отрицание и печатает
  `Цифр: 0, сумма цифр: 0`. Один и тот же код, два разных ответа —
  типичное лицо UB. Поэтому модуль мы берём в `long long`: там
  2 147 483 648 помещается с запасом. Другой путь — вообще не брать
  модуль и работать с отрицательными остатками (`-123 % 10` даёт −3,
  см. каверзу 9). На Junior это редко спрашивают, но упомянуть —
  большой плюс.
- «Цифровой корень: складывай сумму цифр, пока не останется одна цифра
  (9875 → 29 → 11 → 2).» Это цикл поверх нашего цикла — частое
  продолжение. Бонус: цифровой корень равен `1 + (n - 1) % 9` для
  положительных `n`, и это интервьюеру нравится. Проверим: 9874 = 9 ·
  1097 + 1, остаток 1, плюс один — 2. Работает, потому что число и
  сумма его цифр дают одинаковый остаток при делении на 9 (10 = 9 + 1,
  поэтому каждый разряд «весит» по модулю 9 ровно единицу).
- «Переверни число: 123 → 321.» Тот же цикл, но вместо суммы копим
  `rev = rev * 10 + digit`. С защитой от переполнения — см. Приложение В,
  задача 10.

## Часть 2. Три классики без отдельного файла

Эти три задачи решаются в несколько строк, и отдельных файлов в `code/`
под них нет — весь код прямо здесь. Но спрашивают их не реже остальных.

### Задача 9. Проверить чётность числа

**Условие.** Дано целое число. Определи, чётное оно или нечётное.

**Идея.** Школьный способ — остаток от деления: `n % 2 == 0` (см. главу
4). Но на собесе часто хотят увидеть **битовый** приём: у чётного числа
младший бит равен 0, у нечётного — 1. Проверить младший бит можно
операцией `&` (побитовое «И») с единицей.

**Решение:**

```c
#include <stdio.h>

int main(void)
{
    int n = 7;

    if (n % 2 != 0) {
        printf("%d — нечётное\n", n);
    } else {
        printf("%d — чётное\n", n);
    }
    return 0;
}
```

Запуск:

```text
7 — нечётное
```

**Разбор.** Почему я написал `n % 2 != 0`, а не более привычное
`n % 2 == 1`? Потому что для **отрицательных** нечётных `n % 2` даёт не
+1, а −1 (см. каверзу 9), и проверка `== 1` молча провалится: −7 будет
объявлено чётным. Сравнение с нулём такой ошибки не допускает — от знака
оно не зависит.

Битовый вариант выглядит так:

```c
if (n & 1) {
    printf("%d — нечётное\n", n);
}
```

`n & 1` сравнивает биты `n` и числа 1 по позициям. У единицы выставлен
только самый младший бит. Поэтому `n & 1` оставляет от `n` ровно этот
младший бит: 1 у нечётных, 0 у чётных. В `if` ненулевое — это истина
(см. главу 2).

**Что спросят дальше.** «Чем `n & 1` лучше `n % 2`?» Для положительных
чисел — ничем существенным: оба корректны. Проверка `n % 2 != 0`
компилятор с `-O2` превращает ровно в ту же команду, что и `n & 1`, —
я смотрел ассемблер (`cc -O2 -S`), там одна инструкция `andl $1`. Сам
по себе остаток `n % 2` для знакового `n` стоит на пару команд дороже:
компилятору приходится поправлять знак. А вот для отрицательных есть
тонкость, о которой хорошо бы сказать честно.

Стандарт C11 разрешает три представления знаковых чисел: дополнительный
код, обратный код и «знак-величина». Побитовые операции работают с
битами представления, поэтому результат `n & 1` для отрицательного `n`
формально **implementation-defined** — зависит от платформы. В
обратном коде, например, −7 записывается как `...11111000`, и `-7 & 1`
дал бы 0 — «чётное». На любой
реальной машине представление дополнительное (а с C23 оно и вовсе
единственное разрешённое), и `-7 & 1` даёт 1. Но правильный ответ на
собеседовании звучит так: «на нашей платформе — 1, потому что
дополнительный код; переносимо и без оговорок — `n % 2 != 0`».

### Задача 10. Максимум и минимум массива за один проход

**Условие.** Дан массив целых. Найди наибольший и наименьший элементы за
один проход.

**Идея.** Заводим `max` и `min`, инициализируем их **первым элементом**
массива (не нулём! см. подвох ниже) и идём по остальным, обновляя.

**Решение:**

```c
#include <stdio.h>

int main(void)
{
    int a[] = {4, -2, 9, 1, 7, -8, 3};
    int n = (int)(sizeof(a) / sizeof(a[0]));

    int max = a[0];
    int min = a[0];
    for (int i = 1; i < n; i++) {
        if (a[i] > max) {
            max = a[i];
        }
        if (a[i] < min) {
            min = a[i];
        }
    }

    printf("min = %d, max = %d\n", min, max);
    return 0;
}
```

Запуск:

```text
min = -8, max = 9
```

**Разбор.** `sizeof(a) / sizeof(a[0])` — это размер всего массива в
байтах, делённый на размер одного элемента, то есть **число элементов**.
Здесь 28 / 4 = 7. Приём работает, только пока `a` — настоящий массив, а
не указатель (см. подвох ниже).

Цикл стартует с `i = 1`, потому что нулевой элемент уже лежит и в `max`,
и в `min` — сравнивать его с самим собой незачем.

**Сложность.** O(n) времени, два сравнения на каждый элемент, кроме
первого, то есть 2(n − 1) сравнений — примерно 2n. O(1) памяти.

**Что спросят дальше.**

- «Почему инициализируешь первым элементом, а не нулём?» Если поставить
  `max = 0`, а все числа в массиве отрицательные — максимумом ошибочно
  останется 0, которого в массиве нет. То же с `min` и массивом из одних
  положительных. Безопасно стартовать значением **из самого массива**.
- «А если массив пустой?» `a[0]` уже выход за границу — UB. Нужна
  проверка `if (n == 0) return ...;` в самом начале. Пустой ввод — первое,
  о чём спрашивают.
- «Сделай за 1.5n сравнений.» Есть приём: брать элементы **парами**,
  сначала сравнивать их между собой, и меньший сравнивать с `min`, а
  больший с `max`. Получается 3 сравнения на 2 элемента вместо 4, то
  есть около 3n/2 = 1.5n сравнений на весь массив.
- «А если передать массив в функцию и там взять `sizeof`?» Не сработает!
  В функции параметр-массив превращается в **указатель**, и `sizeof`
  вернёт размер указателя (8 байт на этой машине), а не массива. Поэтому
  длину всегда передают **отдельным параметром**: `void f(int *a, int n)`.
  Классический подвох — полный разбор с реальным выводом и
  предупреждением компилятора в Приложении Б, каверза 2.

### Задача 11. FizzBuzz

**Условие.** Числа от 1 до 100. Кратные 3 заменяй на `Fizz`, кратные 5 —
на `Buzz`, кратные и 3, и 5 — на `FizzBuzz`, остальные печатай как есть.

**Идея.** Вся соль — в **порядке** проверок. Самое строгое условие
(кратно 15) должно идти первым, иначе число 15 поймается веткой «кратно
3» и выдаст `Fizz` вместо `FizzBuzz` (полный разбор — в главе 4).

**Решение** (готовый файл — `code/04-fizzbuzz.c` из главы 4):

```c
#include <stdio.h>

int main(void)
{
    for (int i = 1; i <= 100; i++) {
        if (i % 15 == 0) {
            printf("FizzBuzz\n");
        } else if (i % 3 == 0) {
            printf("Fizz\n");
        } else if (i % 5 == 0) {
            printf("Buzz\n");
        } else {
            printf("%d\n", i);
        }
    }
    return 0;
}
```

Первые пятнадцать строк вывода:

```text
1
2
Fizz
4
Buzz
Fizz
7
8
Fizz
Buzz
11
Fizz
13
14
FizzBuzz
```

**Разбор.** В цепочке `if / else if` срабатывает **первая** подходящая
ветка, остальные даже не проверяются. Поэтому «кратно 15» (то же, что
«кратно и 3, и 5») ставим раньше «кратно 3» и «кратно 5». Поменяй
порядок — и на 15-й строке вместо `FizzBuzz` вылезет `Fizz`. Это ровно
та ошибка, ради которой задачу и дают.

**Сложность.** O(n) — одна итерация на число, внутри константа операций.

**Что спросят дальше.** «Сделай без `% 15`, только через `% 3` и `% 5`.»
Собери строку из флагов:

```c
int by3 = (i % 3 == 0);
int by5 = (i % 5 == 0);
if (by3) printf("Fizz");
if (by5) printf("Buzz");
if (!by3 && !by5) printf("%d", i);
printf("\n");
```

Этот вариант легко расширяется (добавить «кратно 7 → Bazz» — две новые
строки, `int by7 = ...` и `if (by7) printf("Bazz");`, и `&& !by7` в
последнем условии; тогда 105 = 3 · 5 · 7 напечатается как
`FizzBuzzBazz`), и интервьюер часто просит именно его: проверить, что ты не
зубрил, а понимаешь структуру. Обрати внимание — `printf` без `\n` внутри
и один общий перевод строки в конце: так `Fizz` и `Buzz` склеиваются в
`FizzBuzz` сами собой. Я сверил: на числах от 1 до 100 обе версии
печатают одно и то же, байт в байт.

## Часть 3. Каверзы: «что выведет / в чём ошибка»

Здесь короткие фрагменты. На собесе их показывают и спрашивают: «что
напечатает?» или «найди ошибку». Цель — не код написать, а проверить,
насколько хорошо ты знаешь язык в деталях. Сначала подумай сам, потом
читай ответ.

Все фрагменты я запускал, завернув каждый в обычную программу:
`#include <stdio.h>`, `#include <limits.h>`, пустая строка,
`int main(void)`, `{`, сам фрагмент, `return 0;`, `}`. Файлы назывались
`k1.c`, `k2.c` и так далее по номеру каверзы — отсюда имена и номера
строк в сообщениях компилятора ниже. Длинные строки сообщений я
перенёс, чтобы влезли в страницу.

Важная общая мысль: у части таких вопросов **нет одного правильного
ответа**. Если фрагмент содержит неопределённое поведение (UB) или
опирается на свойства платформы, ответ «выведет вот столько» просто
неверен. Правильный ответ — назвать это своим именем. Ниже я отмечаю
каждый такой случай.

### Каверза 1. `sizeof('a')` — сколько это?

```c
printf("%zu %zu\n", sizeof(int), sizeof('a'));
```

**Вопрос.** Что выведет? Подсказка-ловушка: `'a'` — это же один символ,
значит 1 байт?

**Ответ.** На этой машине выведет:

```text
4 4
```

Сюрприз в том, что в языке **C** символьный литерал `'a'` имеет тип не
`char`, а **`int`**! Поэтому `sizeof('a')` равен `sizeof(int)`.

Важно: это особенность именно C. В C++ `'a'` — это `char`, и там
`sizeof('a')` равно 1. На собесе по C правильный ответ — «столько же,
сколько `sizeof(int)`».

И вторая половина ответа: число 4 — это **не** гарантия стандарта.
Стандарт требует только, чтобы `int` вмещал хотя бы числа от −32767 до
32767 (то есть имел минимум 16 бит) и чтобы его диапазон был не уже,
чем у `short`. На современных 32- и 64-битных системах `int` — 4 байта,
на 8- и 16-битных микроконтроллерах бывает 2 байта. Единственный размер, зафиксированный
намертво, — `sizeof(char)`, он **всегда** 1: char и есть единица
измерения для `sizeof`.

`%zu` — спецификатор для типа `size_t`, который возвращает `sizeof`
(беззнаковый тип для размеров). Печатать его через `%d` нельзя: по
стандарту несовпадение спецификатора и типа аргумента — UB, а на
практике `size_t` на 64-битной системе шире `int`, и `printf` возьмёт
из аргументов не то количество байт.

### Каверза 2. Целочисленное деление `5 / 2`

```c
printf("%d\n", 5 / 2);
double x = 5 / 2;
printf("%f\n", x);
```

**Вопрос.** Что в обеих строках?

**Ответ.** Реальный запуск:

```text
2
2.000000
```

Первая строка: деление двух **целых** идёт нацело, дробная часть
отбрасывается (см. главу 2), а не округляется. `5 / 2` это 2, а не 2.5 и
не 3. Кстати, `7 / 2` тоже 3, а не 4 — отбрасывание, не округление.

Вторая печатает `2.000000`, а **не** 2.5, и это главный подвох. Хотя
`x` объявлен как `double`, выражение `5 / 2` считается **до** записи в
`x`: оба операнда целые → целочисленное деление → 2 → и уже 2
превращается в `2.0`. Тип переменной слева не влияет на то, как
вычисляется правая часть. Это общее правило Си, и оно ловит очень многих.

Чтобы получить 2.5, дробным должен быть хотя бы один операнд:
`5.0 / 2`, или `(double)5 / 2`, или `5 / 2.0`. Достаточно одного — второй
операнд подтянется к `double` автоматически.

### Каверза 3. `printf("%d", c)` для `char`

```c
char c = 'A';
printf("%d\n", c);
```

**Вопрос.** Что выведет?

**Ответ.**

```text
65
```

Символ в C — это маленькое целое, его **код** (см. главу 2). Код буквы
`A` в таблице ASCII равен 65; стандарт Си ASCII не требует, но на всех
привычных машинах кодировка с ним совпадает. Спецификатор `%d` просит напечатать число, поэтому
печатается не сама буква, а её код. Хочешь увидеть букву `A` —
используй `%c`.

И наоборот полезно помнить: `printf("%c\n", 66)` напечатает `B` — число
истолкуется как код символа. На этой двойственности (символ = число)
держатся трюки вроде перевода регистра из задачи 6 и перевода
символа-цифры в число через `c - '0'`.

### Каверза 4. `char` — знаковый или беззнаковый?

```c
char c = (char)200;
printf("%d\n", c);
```

**Вопрос.** Что выведет — 200 или что-то другое?

**Ответ.** Правильный ответ: **зависит от платформы**, стандарт этого не
фиксирует. Тип `char` в Си — не то же самое, что `signed char` или
`unsigned char`; это **третий**, отдельный тип, и знаковый он или нет,
решает компилятор. Стандарт называет это implementation-defined
поведением.

На этой машине (clang, x86-64, macOS) `char` знаковый, и вывод такой:

```text
-56
```

Откуда −56? Байт `200` в двоичном виде — `11001000`. В знаковый `char`
(от −128 до 127) число 200 не помещается, и что получится при таком
преобразовании, стандарт тоже оставляет на усмотрение компилятора. Все
распространённые компиляторы просто берут те же 8 бит и читают их в
дополнительном коде: старший бит весит не +128, а −128, поэтому
−128 + 64 + 8 = −56. То же самое проще: 200 − 256 = −56. Проверить, какой
`char` у тебя, можно через `<limits.h>`: у нас `CHAR_MIN = -128`,
`CHAR_MAX = 127` — значит, знаковый. На ARM под Linux или на PowerPC ты
увидел бы `CHAR_MIN = 0` и вывод `200`. (Не путай с Mac на процессорах
Apple: это тоже ARM, но Apple сделала `char` знаковым, как на x86.)

**Почему это важно на практике.** Все функции из `<ctype.h>` —
`isalpha`, `isdigit`, `tolower`, `toupper` — принимают `int` и требуют,
чтобы значение было либо `EOF`, либо представимым как `unsigned char`.
Передашь туда знаковый `char` с кодом больше 127 (например, байт из
UTF-8-строки) — получишь отрицательное число, выход за таблицу и UB:

```c
char c = s[i];
if (isalpha(c)) { ... }              /* ОПАСНО: c может быть < 0 */
if (isalpha((unsigned char)c)) { ... }   /* правильно */
```

То же самое с `strcmp`: стандарт требует сравнивать символы **как
`unsigned char`**, иначе строки с русскими буквами сравнивались бы не в
том порядке. Именно поэтому в Приложении Б в самодельной `my_strcmp`
стоит приведение к `unsigned char`.

Хочешь однозначности — пиши `signed char` или `unsigned char` явно.
Голый `char` используй только для текста.

### Каверза 5. `=` вместо `==` в условии

```c
int n = 5;
if (n = 0) {
    printf("ноль\n");
} else {
    printf("не ноль\n");
}
printf("n = %d\n", n);
```

**Вопрос.** Что выведет?

**Ответ.** Реальный запуск:

```text
не ноль
n = 0
```

Здесь стоит один `=` (присваивание), а не `==` (сравнение). Поэтому
`n = 0` сначала **кладёт** 0 в `n`, а потом результатом всего выражения
становится само присвоенное значение — 0. Ноль в условии — это «ложь»,
поэтому срабатывает ветка `else`. Заодно `n` теперь равно 0, хотя мы
вроде бы только «проверяли» — вторая строка вывода это подтверждает.

Если бы было `if (n = 5)`, условие стало бы истинным (5 — ненулевое), и
такие баги особенно коварны: код «как будто работает».

Спасает компилятор. Собери с `-Wall` — и он сам покажет пальцем:

```text
k5.c:7:11: warning: using the result of an assignment as a condition
without parentheses [-Wparentheses]
    7 |     if (n = 0) {
      |         ~~^~~
k5.c:7:11: note: place parentheses around the assignment to silence
this warning
    7 |     if (n = 0) {
      |           ^
      |         (    )
k5.c:7:11: note: use '==' to turn this assignment into an equality
comparison
    7 |     if (n = 0) {
      |           ^
      |           ==
1 warning generated.
```

(Первая подсказка — «поставь
лишние скобки, если присваивание задумано», вторая — «или ты хотел
`==`».)

Защитный приём — «йода-условие»: писать `if (0 == n)`; тогда опечатку
`0 = n` компилятор отвергнет как ошибку (константе присвоить нельзя).
Приём спорный — читается непривычно, — но на собеседовании про него
приятно знать.

### Каверза 6. Лишняя `;` после `for(...)`

```c
int sum = 0;
for (int i = 1; i <= 5; i++);
{
    sum += i;
}
printf("%d\n", sum);
```

**Вопрос.** Найди ошибку. Что не так?

**Ответ.** Лишняя точка с запятой сразу после `for(...)`. Эта `;` —
**пустое тело цикла**. То есть цикл крутится 5 раз и ничего не делает.
А блок в фигурных скобках ниже — это уже **обычный блок**, не связанный
с циклом; он выполнится **один раз**.

Хуже того: этот фрагмент вообще не скомпилируется — `i` объявлена внутри
`for` и за его пределами не видна. Вот что реально говорит clang:

```text
k6.c:9:16: error: use of undeclared identifier 'i'
    9 |         sum += i;
      |                ^
k6.c:7:33: warning: for loop has empty body [-Wempty-body]
    7 |     for (int i = 1; i <= 5; i++);
      |                                 ^
k6.c:7:33: note: put the semicolon on a separate line to silence this
warning
1 warning and 1 error generated.
```

Обрати внимание: компилятор выдал и ошибку, и предупреждение про пустое
тело — то есть увидел обе проблемы разом.

Если бы `i` была объявлена снаружи цикла (`int i;` и
`for (i = 1; ...)`), код собрался бы — с тем же предупреждением про
пустое тело — и напечатал `6`: цикл ничего не сделал, а блок один раз
прибавил к нулю значение `i`, оставшееся после цикла (6). Логика при
этом всё равно сломана: ждали 1+2+3+4+5 = 15. Я проверил и этот
вариант — вывод действительно `6`.

Мораль: точка с запятой сразу после `for`, `while` или `if` — почти
всегда ошибка. Настоящий пустой цикл (например, `while (*p++);`)
пишут либо с `{}`, либо с `;` на отдельной строке — именно это и
советует clang.

### Каверза 7. `printf("%d %d", i++, ++i)`

```c
int i = 1;
printf("%d %d\n", i++, ++i);
```

**Вопрос.** Что выведет?

**Ответ.** Честный ответ: **неизвестно**, «правильного» числа тут нет.
Это **неопределённое поведение** (undefined behavior, UB). В одном
выражении переменная `i` меняется дважды (`i++` и `++i`), и эти два
изменения ничем не упорядочены друг относительно друга (unsequenced).
Порядок вычисления аргументов `printf` стандарт оставляет
**неуказанным** (unspecified): компилятор выбирает его сам и не обязан
об этом сообщать. Само по себе это ещё не UB. Но модификация одного
объекта дважды без упорядочивания прямо объявлена неопределённым
поведением (C11, раздел 6.5, пункт 2) — вот это уже UB.

Компилятор про это знает и предупреждает:

```text
k7.c:7:24: warning: multiple unsequenced modifications to 'i'
[-Wunsequenced]
    7 |     printf("%d %d\n", i++, ++i);
      |                        ^   ~~
1 warning generated.
```

Если запустить, на этой машине печатается `1 3` — и с `-O0`, и с `-O2`.
Но это **не ответ на вопрос**. Другой компилятор, другая версия того же
компилятора или другие флаги имеют полное право выдать `2 3`, `1 2` или
вообще что угодно: программа некорректна, и обсуждать её вывод
бессмысленно.

Если на собесе спрашивают «что выведет» — правильный ответ не «2 3» и не
«1 3», а именно: «это UB, результат не определён, так писать нельзя».
Интервьюер проверяет, узнаёшь ли ты опасную конструкцию, а не считаешь
ли в уме «как у меня на ноутбуке». А если он настаивает, что ответ
один-единственный, — покажи ему `-Wunsequenced`.

Лечится разнесением по строкам:

```c
int a = i++;   /* теперь порядок однозначен */
int b = ++i;
printf("%d %d\n", a, b);
```

Между полными выражениями (то есть между `;`) точка следования есть, и
всё определено: `a` получит 1, `b` — 3.

### Каверза 8. Неинициализированная переменная

```c
int sum;
for (int i = 1; i <= 5; i++) {
    sum += i;
}
printf("%d\n", sum);
```

**Вопрос.** Что выведет?

**Ответ.** Заранее **неизвестно**, и это снова UB, а не «какое-то
число». `sum` объявлена, но не инициализирована — в локальной переменной
лежит мусор (что осталось в этой ячейке стека). Без оптимизации к этому
мусору честно прибавляется 1+2+3+4+5 = 15.

Вот три запуска подряд одной и той же программы, собранной с `-O2`:

```text
-1234390016
-1267702784
-1123482624
```

Числа разные при каждом запуске. Откуда они? Я заглянул в ассемблер
(`cc -O2 -S`): от цикла там не осталось ничего, ни одного сложения —
только вызов `printf`. Компилятор вправе считать, что UB не бывает, и
выбросил вычисление целиком, а напечаталось то, что случайно лежало в
регистре для второго аргумента. Собранная с `-O0` та же программа у
меня три раза подряд напечатала одно и то же `1461713879` — тоже
мусор, просто стабильный. Ни то ни другое не 15, и ни на что из этого
нельзя полагаться. Может «повезти» и вывестись 15, если в ячейке был
ноль, — и это худший исход: баг спрячется и вылезет у пользователя.

Компилятор ловит это сам:

```text
k8.c:8:9: warning: variable 'sum' is uninitialized when used here
[-Wuninitialized]
    8 |         sum += i;
      |         ^~~
k8.c:6:12: note: initialize the variable 'sum' to silence this warning
    6 |     int sum;
      |            ^
      |             = 0
1 warning generated.
```

Фикс — один символ: `int sum = 0;`. Любой накопитель перед циклом
обнуляй (сумма — в 0, произведение — в 1). И не игнорируй
предупреждения: `-Wall` тут буквально дописал за тебя правильный код.

Отдельно запомни: **глобальные** и `static`-переменные обнуляются
автоматически, а локальные — нет. Отсюда и путаница у новичков: «у меня
же в прошлый раз работало».

### Каверза 9. Остаток от отрицательного числа

```c
printf("%d %d\n", -7 / 2, -7 % 2);
```

**Вопрос.** Что выведет?

**Ответ.**

```text
-3 -1
```

В современном C (стандарт C99 и новее) деление целых округляется
**к нулю**: `-7 / 2` это −3, а не −4. Раньше, в C89, направление
округления было отдано на откуп компилятору, — но это уже история.

Остаток подчиняется тождеству `(a / b) * b + a % b == a`. Подставим:
`(-3) * 2 + x == -7`, значит `x == -1`. Отсюда `-7 % 2` равен −1, а не
+1. Проще запомнить так: **знак остатка совпадает со знаком делимого**
(если остаток не ноль). Обрати внимание: это не тот остаток, что в
школьной математике. Там −7 = 2 · (−4) + 1, остаток 1 — при делителе 2
он всегда 0 или 1, а для любого положительного делителя — от 0 до
делителя минус один.
Оператор `%` в Си — не «математический остаток», а «то, что осталось
после деления с отбрасыванием дробной части».

Практический вывод: проверять нечётность через `n % 2 == 1` **опасно** —
для отрицательных нечётных получится −1, и проверка провалится. Пиши
`n % 2 != 0`. Это прямая связь с задачей 9 про чётность.

Ещё одно применение того же правила — разворот числа в Приложении В
(задача 10): там `-123 % 10` даёт −3, и знак сохраняется сам собой, без
единого `if`.

## Ошибки, на которых сыплются в этих задачах

Собрал в одном месте то, что чаще всего ломается именно в задачах этого
уровня. Пробеги глазами перед собеседованием.

- **Накопитель без начального значения.** `int sum;` вместо
  `int sum = 0;` — и в сумме мусор (каверза 8). Для произведения
  начальное значение 1, не 0.
- **Старт `max`/`min` с нуля.** На массиве из одних отрицательных
  максимум окажется нулём, которого в массиве нет. Стартуй элементом
  массива (задача 10).
- **Забытая проверка `scanf`.** `scanf("%d", &n)` возвращает число
  прочитанных значений. Не проверил — работаешь с мусором в `n`.
- **`sizeof` массива внутри функции.** Даёт размер указателя, а не
  массива. Длину передавай параметром.
- **`n % 2 == 1` для отрицательных.** Даёт −1, проверка проваливается
  (каверза 9).
- **Пустая строка и `strlen(s) - 1` в `size_t`.** Беззнаковое
  вычитание заворачивается в огромное число, и цикл уходит за границы.
  Держи индексы в `int` или проверяй пустоту отдельно.
- **`-n` для `INT_MIN`.** Переполнение знакового, то есть UB. Всплывает
  в «возьми модуль» (задача 8).
- **`ctype.h` без `(unsigned char)`.** UB на байтах с кодом больше 127
  (каверза 4).
- **Одна переменная меняется дважды в одном выражении.** UB (каверза 7).
  Разнеси по строкам.
- **Точка с запятой после `for`/`while`/`if`.** Пустое тело, логика
  ломается молча (каверза 6).

## Тренировочные задачи

Решай без подглядывания в разборы. Каждая — это чуть изменённое условие
из тех, что уже разобраны: интервьюеры именно так и «дожимают».

1. Перепиши задачу 3 (палиндром) так, чтобы регистр не имел значения и
   игнорировались все не-буквы. Проверь на строке
   `"A man, a plan, a canal: Panama"` — должно получиться «палиндром».
   Ещё проверки: `"Level"` и `"No 'x' in Nixon"` — палиндромы,
   `"hello"` и `"ab!"` — нет, пустая строка и `"!!"` — палиндромы (букв
   нет, сравнивать нечего). Подсказка: сравнивай
   `tolower((unsigned char)s[left])` и `tolower((unsigned char)s[right])`.
2. Допиши задачу 5 (второй максимум) так, чтобы она правильно работала на
   массиве `{5, INT_MIN}`. Подсказка: замени сравнение с `INT_MIN` на
   отдельный флаг. Ожидаемо: для `{5, INT_MIN}` и для `{INT_MIN, 5}` —
   `Максимум: 5, второй: -2147483648`; для `{5, 5, 5}` и для `{42}` —
   по-прежнему «Второго по величине нет.»; для массива из задачи —
   `Максимум: 9, второй: 7`. Учти, что флаг нужен и для максимума: у
   второго максимума стартового значения «меньше всех» больше нет.
3. Реализуй счётчик цифр из задачи 8 для `long long` и убедись, что для
   `LLONG_MIN` программа не падает и не выдаёт мусор. Подвох: у
   `long long` нет типа шире, куда можно убежать от `-LLONG_MIN`, так
   что модуль не бери, а работай с отрицательными остатками (`n % 10`
   для отрицательного `n` даёт цифру со знаком минус — возьми её
   модуль, он от 0 до 9) и цикл веди до `n != 0`. Ожидаемо: для
   −9223372036854775808 — 19 цифр, сумма 89; для
   9223372036854775807 — 19 цифр, сумма 88; для 0 — 1 цифра, сумма 0.
4. Напиши функцию `int count_words(const char *s)`, которая считает
   слова, разделённые пробелами. Проверь на строках `""`, `"   "`,
   `"one"`, `"  dva   slova  "`. Ожидаемо: 0, 0, 1, 2. Подсказка:
   слово начинается там, где после пробела (или в самом начале строки)
   идёт не пробел, — как в главе 10.
5. Напиши «обратный FizzBuzz»: программа получает строку `Fizz`, `Buzz`,
   `FizzBuzz` или число и печатает наименьшее число от 1 до 100, которое
   ей соответствует. Ожидаемо: `Fizz` → 3, `Buzz` → 5, `FizzBuzz` → 15,
   `7` → 7. А для `9` ответа нет: число 9 FizzBuzz печатает как `Fizz`,
   так что строку `9` не выдаёт никогда, — программа должна так и
   сказать.
6. Возьми задачу 7 (простое число) и верни «наивное» условие
   `d * d <= n` вместо `d <= n / d`. Собери с `-fsanitize=undefined` и
   введи 2147483647. Ожидаемо: санитайзер сообщит
   `signed integer overflow: 46341 * 46341 cannot be represented in
   type 'int'`, а обычная сборка с `-O2` ответит «не простое», хотя
   2147483647 простое. Для всех `n` до 200 000 обе версии отвечают
   одинаково — ошибка живёт только у самого края диапазона `int`, и
   поэтому её так трудно поймать тестами.

## Мини-резюме

Что стоит унести из этого приложения — не сами решения (их в интернете
тысячи), а привычки, которые отличают подготовленного кандидата:

- **Краевые случаи проговаривай вслух**: пустой массив, один элемент,
  ноль, отрицательное, дубликаты, переполнение. Интервьюер часто ставит
  плюс именно за то, что ты сам про них вспомнил.
- **Помни про типы и переполнение.** `int` лопается на ~2 млрд; символьный
  литерал — это `int` в C; деление целых идёт нацело; знаковость `char`
  зависит от платформы. Эти четыре факта спрашивают чаще всего.
- **Знай про опасные приёмы, но не используй их без нужды.** XOR-своп,
  арифметический обмен — рассказать можешь, в код кладёшь `temp`.
- **UB называй своим именем.** Увидел `i++` и `++i` в одном выражении,
  неинициализированную переменную, изменение строкового литерала,
  переполнение знакового — отвечай «это неопределённое поведение», а не
  угадывай результат. И отдельно называй implementation-defined:
  размер `int`, знаковость `char` — тут ответ есть, но он свой на каждой
  платформе.
- **Компилируй с `-Wall -Wextra`.** Четыре каверзы из девяти в третьей
  части (с 5-й по 8-ю) компилятор ловит сам — мы это только что видели
  по его сообщениям.
